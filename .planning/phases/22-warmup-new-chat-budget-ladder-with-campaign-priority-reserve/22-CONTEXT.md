<decisions>
## Зафиксированные решения

### Базовые принципы
- **D-01:** Гейтим только аккаунты в warmup-пуле; остальные работают как сейчас.
- **D-02:** Бюджет = «новых чатов в сутки» (скользящие 24 ч, как в существующем кап Phase 12 — без взрывов в полночь).
- **D-03:** Рассылка всегда в приоритете: warmup тратит только то, что рассылке сегодня не нужно.
- **D-04:** Лестница: недели 1–3 → 3/день, неделя 4 → 4, неделя 5 → 6, неделя 6 → 8, после 42 дней — кап 8 навсегда. Всё редактируется.

### 1. Схема данных — миграция 053
- **D-05:** `warmup_settings` (существующая таблица, паттерн как у topics): добавляем `levels` JSONB (массив `{days, new_chats_per_day}`), `graduated_cap` INT (дефолт 8), `max_messages_per_day` INT (дефолт 60 — вместо старой лестницы сообщений). NULL/пусто = код-дефолты, поведение без настроек не меняется.
- **D-06:** Новая таблица `sender_first_contacts` (`sender_id`, `peer_phone`, `first_contact_at`) с PK по паре — единственный источник правды «этому peer'у уже писали первым». Бэкфилл в той же миграции из `conversations` + `warmup_messages` (идемпотентно, `ON CONFLICT DO NOTHING`), чтобы существующие диалоги не посчитались новыми.

### 2. Queue worker — гейт рассылки
- **D-07:** В SQL-выборке `_process_next_for_sender` (ветка «new dialog», queue.py:490) добавляется третье условие: если sender активен в warmup-пуле — `COUNT(sender_first_contacts за 24ч) < бюджет_уровня`. Follow-up'ы и ответы не трогаем (как и сейчас). Исчерпан бюджет → opener просто ждёт, не сгорает.
- **D-08:** Бюджет уровня считается в Python по `enrolled_at` и передаётся биндом (по образцу `expected_now` из Phase 13). После успешной отправки cold opener'а — insert в реестр.

### 3. Warmup worker — три изменения
- **D-09:** Убираем лестницу сообщений (LEVEL_CONFIG 5→120/день) → один настраиваемый `max_messages_per_day`. Pacing (≥5 мин между сообщениями, 5 мин–2 ч в диалоге) остаётся.
- **D-10:** Создание новой пары тратит бюджет инициатора. Пара «знакомых» аккаунтов (уже есть в реестре) — бесплатна, как сейчас. Новая пара создаётся только если у инициатора после резерва остаётся ≥1 слот.
- **D-11:** Приоритет рассылки = резерв: остаток = бюджет − потрачено_за_24ч − pending cold openers сендера в очереди на сегодня. Warmup берёт слот только из положительного остатка — рассылка никогда не недополучит.
- **D-12:** Бонус к безопасности — выбор инициатора: первым в новой паре пишет более старый/прогретый аккаунт. Новичок в пуле только получает входящие и отвечает (ответы бюджет не тратят) — его лимит 3/день целиком остаётся рассылке, а входящие чаты для Telegram выглядят максимально естественно.

### 4. API
- **D-13:** `GET/PUT /warmup/settings` — уровни (массив), `graduated_cap`, `max_messages_per_day`; валидация: дни > 0, лимиты 1–50, предупреждение зелёного коридора отдаёт бэкенд (поле `recommended` в ответе).
- **D-14:** `GET /warmup/pool` — по каждому участнику: `level`, `day_in_pool`, `new_chats_24h`, `budget`, `reserved_for_campaigns`, `remaining`.
- **D-15:** `GET /warmup/stats` — агрегаты по уровням.
- **D-16:** Регенерация openapi.json + типов для Lovable.

### 5. Frontend (Lovable, отдельный репо)
- **D-17:** Страница прогрева: редактор уровней (4 строки: «дни» + «новых чатов/сутки»), кап после прогрева, лимит сообщений, зелёный коридор (подсветка + предупреждение при превышении рекомендованных), в таблице пула — бейдж уровня и прогресс-бар «новые чаты сегодня 2/3». Handoff-дока с макетом контрактов.

### 6. Тесты и деплой
- **D-18:** Юнит + интеграционные через test-overlay: расчёт уровня по дням, гейт в очереди (opener блокируется/follow-up проходит), резерв под рассылку, выбор инициатора, идемпотентность бэкфилла.
- **D-19:** Деплой: миграция авто-применится при `docker compose up -d --build api`, ребилд listener не нужен (warmup и очередь живут в api-процессе).

</decisions>
