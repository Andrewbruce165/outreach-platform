# Phase 13: Even pacing across sending window (smooth new-dialog distribution) - Context

**Gathered:** 2026-06-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Распределять открытие **новых холодных диалогов** равномерно по активному окну
рассылки кампании, а не выпаливать дневной лимит за первые часы. Темп производный:
`целевой_интервал = ширина_окна / max_new_dialogs_per_day` (вход — per-sender лимит
из Phase 12). Механизм — **доп. гейт в queue-воркере поверх существующего**
per-send интервала; применяется **только к новым диалогам**, follow-ups (как в
Phase 12) не троттлятся.

**Вне scope:**
- Любые поля API / колонки БД / UI / openapi-регенерация — фаза целиком в `queue.py`
  (D-13: авто-вывод темпа, без новой поверхности конфига).
- Изменение per-sender лимитов (4/20/150) и `MAX_NEW_CONTACTS_PER_HOUR=15` — остаются
  как есть, новый темп лишь стыкуется с ними (CLAUDE.md guard).
- Изменение самого потолка `max_new_dialogs_per_day` (это Phase 12).
- Троттлинг follow-up / AI-ответов.
- Аналитика/дашборд по темпу новых диалогов — отдельная фича.
</domain>

<decisions>
## Implementation Decisions

### Формула активного окна (целевой интервал)
- **D-01:** Знаменатель — **сырое окно** `(work_hour_end − work_hour_start)`, без
  отдельного вычета длинных пауз. Целевой интервал = `ширина_окна /
  max_new_dialogs_per_day`. Просто и предсказуемо. (При 11ч/50 ≈ 13 мин.)
- **D-02:** `work_days_mask` на знаменатель **не влияет** — лимит дневной, маска лишь
  определяет, шлём ли в этот день вообще (существующая working-window логика).
- **D-03:** **Пол интервала** — целевой интервал никогда не опускается ниже базового
  20–55с-гейта: фактический минимальный зазор для нового диалога = `max(целевой,
  базовый_per_send)`. Если окно физически не вмещает лимит при таком поле — лимит
  просто **не выбирается** (безопасность важнее объёма), это осознанное следствие.

### Политика догона (catch-up при отставании)
- **D-04:** **Гибрид с ограничением всплеска.** Догон есть, но НЕ быстрее существующих
  гейтов: базовый 20–55с per-send, `4/мин`, `15 новых контактов/час`,
  `MAX_NEW_CONTACTS_PER_HOUR`. Никакого отдельного burst-механизма — существующие
  гейты и есть потолок скорости догона. Полный burst (игнор интервала) — **отклонён**
  (снова даёт пачку, противоречит цели фазы). «Без догона» (жёсткий min-gap) —
  **отклонён** (лимит почти никогда не выбирается при любом сбое).
- **D-05:** Механика темпа — модель **«ожидаемо-к-моменту окна»**, НЕ фиксированный
  min-gap: `ожидается = (прошло_окна / всё_окно_сегодня) × max_new_dialogs_per_day`;
  если фактически открыто меньше ожидаемого — новый диалог eligible сейчас (под
  базовыми гейтами), иначе ждём. Это естественно даёт и ровный темп, и ограниченный
  догон. (Точный SQL-shape — усмотрение планнера, см. Discretion.)
- **D-06:** **Числитель пейсинг-проверки** («сколько новых уже открыто к моменту»)
  считается **от старта СЕГОДНЯШНЕГО окна** кампании, а НЕ trailing-24h. Это
  ОТЛИЧАЕТСЯ от счётчика потолка Phase 12 (D-02/D-05 фазы 12: trailing-24h rolling).
  Два разных счётчика — не путать: Phase 12 = «не превысить дневной потолок»,
  Phase 13 = «насколько ровно идём внутри сегодняшнего окна».

### Батчинг пула (семантика при per-sender лимите)
- **D-07:** **Каждый sender пейсит независимо.** Phase 12 сделал лимит per-(sender,
  campaign), т.е. аккаунты уже изолированы. «Батчинг пула» из роадмапа (писался до
  Phase 12) **редуцируется к per-sender темпу** — никаких явных батч-групп, никакого
  нового уровня координации поверх per-sender. Роадмаповское «1 новый диалог каждые
  3–5 мин внутри батча» = per-sender целевой интервал с дрожанием.
- **D-08:** **Дрожание (jitter) темпа — обязательно, не усмотрение.** Целевой интервал
  плавающий (случайный сдвиг к интервалу, напр. ±20–30%), чтобы открытия не строились
  в машинную сетку. Цель — даже при догоне несколько новых диалогов НЕ должны уходить
  в один момент / с разницей в пару секунд. Каждый sender и так стартует со своим
  случайным сдвигом (независимый пейсинг де-синхронизирует аккаунты), базовый
  20–55с-гейт держит per-sender зазор — jitter добавляет разброс самого темпа поверх.

### Поверхность конфига / стыковка
- **D-09:** **Авто-вывод темпа, без новых полей.** Ровный темп всегда включён, интервал
  выводится из окна и `max_new_dialogs_per_day`. НЕТ новых колонок БД / полей API /
  UI / openapi-регенерации. Вся логика — внутри queue-воркера. Per-campaign режим
  even/burst — **отклонён** (лишняя миграция+API+UI). Глобальный фича-флаг —
  рассмотрен, не выбран (можно вернуть позже при необходимости rollback).
- **D-10:** Целевой интервал — **дополнительный гейт ПОВЕРХ** существующего per-send
  интервала, берётся `max(целевой_new_dialog, базовый_20–55с)`. Базовый интервал,
  fatigue-фактор и длинные паузы остаются нетронутыми (CLAUDE.md guard); новый темп —
  отдельный предикат для new-dialog элементов, follow-ups его не видят.

### Claude's Discretion
- Точный SQL-shape пейсинг-проверки (D-05/D-06): correlated subquery vs CTE vs
  window-count — на усмотрение планнера, лишь бы сохранить LIMIT 8 / `FOR UPDATE OF mq
  SKIP LOCKED` семантику и не сломать per-campaign working-window re-check (Phase 4 D-15)
  и Phase 12 new-dialog cap предикат.
- Точная величина jitter (D-08) в рамках «плавающих интервалов» роадмапа (ориентир ±20–30%).
- Где разместить новые константы темпа (модульные vs inline) — по образцу существующих
  rate-констант в queue.py.
- Как именно вычислять «прошло_окна / всё_окно» с учётом per-campaign timezone и
  пересечения полуночи (использовать существующий `_campaign_in_working_window` контекст).
</decisions>

### Reusable Assets
- **Phase 12 new-dialog предикат** (`queue.py:300-333`) — `EXISTS prior sent` (follow-up
  bypass) + per-(sender,campaign) `COUNT(DISTINCT recipient_phone)` за trailing-24h.
  Новый пейсинг-предикат встраивается рядом в тот же SELECT, не дублируя дедуп.
- **`_campaign_in_working_window`** (`queue.py:73-91`) — уже знает per-campaign tz, окно,
  маску; даёт «ширину окна» и «сколько прошло» без новой инфраструктуры.
- **Базовый interval-gate с fatigue** (`queue.py:504-528`) — образец «зазор от последней
  отправки»; целевой интервал — `max` поверх него (D-10).
- **Рандомизация** уже всюду (`random.uniform`/`random.randint` для интервалов и пауз) —
  jitter (D-08) делается тем же приёмом.

### Established Patterns
- Item-selection в `_process_next_for_sender`: JOIN campaigns + post-filter working-window
  (Phase 4 D-15) + Phase 12 new-dialog cap + `FOR UPDATE OF mq SKIP LOCKED` LIMIT 8 —
  пейсинг-предикат обязан встроиться сюда, не сломав эти инварианты.
- `_check_rate_limits` — per-tick gate (`return False` → весь tick пропущен). Пейсинг
  НЕ туда (иначе блокировал бы follow-ups), а в per-item выборку — как Phase 12 (D-07).
- Эмпирические константы темпа (MIN/MAX_SEND_INTERVAL, LONG_PAUSE_*) — менять только в
  рамках этой фазы и с явным обсуждением; здесь они НЕ меняются, добавляется лишь новый
  верхний гейт темпа поверх (CLAUDE.md guard соблюдён).

### Integration Points
- `app/services/queue.py` `_process_next_for_sender` — единственная точка изменения
  (новый пейсинг-предикат + клампинг интервала). Других файлов фаза не трогает.
- Новые константы темпа — в блок rate-config (`queue.py:39-69`).

### Enqueue context (важно для определения «нового диалога»)
- `CampaignEnqueueWorker` кладёт в очередь только холодные первые касания (дедуп по
  conversations). AI-ответы идут мимо очереди через listener. Поэтому пейсинг троттлит
  именно холодные первые касания — ровно те элементы, что и должен (follow-up/re-contact
  через allow_recontact остаются eligible, D-10).

<specifics>
## Specific Ideas

- **Acceptance-ориентир (роадмап):** при `max_new_dialogs_per_day=50` и окне 9–20 новые
  диалоги открываются размазанно по окну (≈ целевой интервал), а не пачкой в первый час;
  внутри per-sender темпа интервал ~3–13 мин с дрожанием; follow-ups идут вне этого темпа.
- **Jitter — явное требование пользователя:** новые диалоги не должны уходить
  одновременно или с разницей в пару секунд даже при догоне; темп плавающий.
</specifics>
