## Decisions Made

### Chosen regex

```
r"https://[a-z0-9-]+\.lovableproject\.com$"
```

Why:
- **Anchored `$`** — prevents `https://abc.lovableproject.com.evil.com` from matching (Pitfall 7 documented attack vector).
- **`[a-z0-9-]+`** — Lovable's auto-generated subdomain charset (lowercase alpha + digits + hyphens; never underscores or uppercase).
- **Backslash-escaped dots** — `.lovableproject.com` not `lovableproject.com` regex substring (would match `xlovableproject.com`).
- **Explicit subdomain requirement** — bare `https://lovableproject.com` (no subdomain) rejected. Defence against future Lovable marketing pages accidentally hitting the API.

### Env override path

Production customers can tighten by setting `CORS_ALLOWED_ORIGIN_REGEX` in `.env`. Example for a vanity-domained Lovable deployment:

```
CORS_ALLOWED_ORIGIN_REGEX=https://[a-z0-9-]+\.acme\.lovable\.app$
```

The default is liberal-by-design for the v1 launch window; customers in regulated industries (banking / health) should narrow to a specific subdomain pattern post-handoff.

### auth.py change scope

Strictly comments and a docstring paragraph. Zero new functions, zero removed functions, no `from jose import jwt` modification, no `algorithms=["HS256"]` modification. ## User Setup Required

Supabase HS256 pinning is a **customer-side action**, not an automated step:

> In Supabase Dashboard → Settings → API → JWT Settings → set **Algorithm = HS256**.

This is documented in the handoff bundle (`lovable-handoff/AGENTS.md` — created in plan 05.1-05) so customers running through the bundle find it before they hit a 401 on their first JWT. The inline Pitfall 3 comment in `app/utils/auth.py` is the bidirectional anchor.

No code-side environment variable change is required for the CORS widening — the default regex matches Lovable's standard subdomain pattern out of the box. Customers who want to narrow may set `CORS_ALLOWED_ORIGIN_REGEX` in their `.env`.
