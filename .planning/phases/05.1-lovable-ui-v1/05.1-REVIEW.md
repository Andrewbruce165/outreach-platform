## Critical Issues

### CR-01: `auto_pause_scope` CHECK constraint excludes NULL — ORM declares column nullable

**File:** `migrations/018_phase5_1.sql:48-49`
**Also affects:** `app/models/__init__.py:175`

**Issue:** The `voice_baseline` CHECK at line 34 correctly uses `CHECK (voice_baseline IS NULL OR ...)`. The `auto_pause_scope` CHECK at line 49 does NOT — it is written as:

```sql
CHECK (auto_pause_scope IN ('conversation','contact','campaign'))
```

In Postgres, a CHECK constraint evaluates to `false` (not `true`) when the column is NULL if there is no `IS NULL OR` guard — **unless the expression returns NULL**, in which case Postgres treats it as passing. Critically, `NULL IN (...)` returns NULL (not false) in Postgres, so Postgres WILL actually pass NULL through this CHECK. However, any future query that sets `auto_pause_scope = NULL` explicitly via an `UPDATE` (not "leave it NULL") could behave unexpectedly because the ORM sets the value to `None` for pre-05.1 rows returned through the PATCH path.

More concretely: the ORM at `models/__init__.py:175` declares `nullable=True` with `server_default="conversation"`, meaning the column CAN be NULL at the Python layer if a PATCH sends `auto_pause_scope=null`. This creates a deliberate inconsistency versus `voice_baseline` — which was consciously authored with `IS NULL OR` precisely for this nullable scenario. The missing guard appears to be an oversight.

**Fix:** Mirror the `voice_baseline` pattern:

```sql
ALTER TABLE ai_contexts DROP CONSTRAINT IF EXISTS ai_contexts_auto_pause_scope_check;
ALTER TABLE ai_contexts ADD CONSTRAINT ai_contexts_auto_pause_scope_check
    CHECK (auto_pause_scope IS NULL OR auto_pause_scope IN ('conversation','contact','campaign'));
```

Add this as a one-liner in a new migration (e.g., `019_fix_auto_pause_scope_check.sql`). It is a no-op on all current production data since `NULL IN (...)` already passes, so no data migration is needed.

### CR-02: Null pointer dereference in `_resolve_or_create_workspace` race path

**File:** `app/utils/auth.py:231-234`

**Issue:** After the `async with db.begin()` block auto-creates a workspace, the code does a post-commit re-SELECT intended to handle the parallel-request race condition. If the race occurs (two simultaneous first-ever requests for the same `supabase_user_id`, as documented in the existing Pitfall 5 comment), one of the two `COMMIT` calls will succeed and the other will get a duplicate-key error at the `UserWorkspace` INSERT — but this IntegrityError is **not caught**. It propagates out of `async with db.begin()` as a 500.

Even ignoring the race, `result.scalars().first()` at line 231 can theoretically return `None` if the row was deleted between the commit and the re-SELECT (pathological but possible). Line 234 then immediately does `canonical_uw.workspace_id`, causing `AttributeError: 'NoneType' object has no attribute 'workspace_id'` — a 500 with no structured error body.

**Fix:** Guard the re-SELECT result and catch the IntegrityError from the concurrent-creation race:

```python
try:
    async with db.begin():
        workspace = Workspace(name=workspace_name)
        db.add(workspace)
        await db.flush()
        new_uw = UserWorkspace(
            supabase_user_id=supabase_user_id,
            workspace_id=workspace.id,
            role="owner",
        )
        db.add(new_uw)
except IntegrityError:
    # Race: another request already created this workspace — fall through to re-SELECT
    await db.rollback()

result = await db.execute(
    select(UserWorkspace).where(
        UserWorkspace.supabase_user_id == supabase_user_id
    ).order_by(UserWorkspace.created_at.asc())
)
canonical_uw = result.scalars().first()
if canonical_uw is None:
    raise HTTPException(status_code=500, detail={"code": "WORKSPACE_CREATE_FAILED",
                                                  "message": "Workspace creation failed unexpectedly"})
```

### WR-01: LIKE metacharacter injection in `_generate_duplicate_name`

**File:** `app/routers/agents.py:142-150`

**Issue:** Agent names can contain `%` and `_` characters (no restriction in `AgentCreate.name: constr(min_length=1, max_length=100)`). The duplicate-name helper builds:

```python
pattern_with_n = f"{base_name} (copy %)"
```

and passes it as `:pattern` in a `LIKE` clause:

```sql
AND (name = :exact OR name LIKE :pattern)
```

A name like `50% off` produces the pattern `50% off (copy %)`, where the `%` in `50%` is treated as a LIKE wildcard. This causes the query to return more rows than intended — for example, it would match `50x off (copy 2)` or `50% off (copy 5)` — causing `_generate_duplicate_name` to skip names that are actually free. The result is the naming logic jumps to a higher copy number than necessary, which is a correctness bug.

**Fix:** Escape LIKE metacharacters in the constructed pattern (Postgres uses `\` or any ESCAPE character):

```python
def _escape_like(s: str) -> str:
    return s.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_")

pattern_no_n = f"{_escape_like(base_name)} (copy)"
pattern_with_n = f"{_escape_like(base_name)} (copy %)"
```

And add `ESCAPE '\\'` to the SQL:

```sql
AND (name = :exact OR name LIKE :pattern ESCAPE '\\')
```

### WR-02: `status_filter` query param on `GET /campaigns` is unvalidated

**File:** `app/routers/campaigns.py:410-420`

**Issue:** `status_filter: Optional[str]` accepts any string. An invalid value like `status=runnin` (typo) silently returns an empty list instead of a 422 error. More importantly, a value like `status='; DROP TABLE--` would be bound as a parameter (not SQL-injectable) but would still silently return an empty result, potentially masking bugs in the frontend.

The correct approach is to use `Literal` to get FastAPI's built-in 422 validation, consistent with how `scope` and `since` params are handled in the analytics endpoints:

**Fix:**

```python
from typing import Literal, Optional

@router.get("", response_model=CampaignListResponse)
async def list_campaigns(
    status_filter: Optional[Literal["draft", "running", "paused", "done"]] = Query(
        default=None, alias="status"
    ),
    ...
```

### IN-01: `constr` is a Pydantic v2 soft-deprecated alias

**File:** `app/schemas/__init__.py:1,427-428,433,458,525,546,547,569,574`

**Issue:** `constr(...)` is carried over from Pydantic v1 and still works in Pydantic v2 (≥2.8 per `requirements.txt`), but it is considered legacy. The canonical v2 spelling is `Annotated[str, StringConstraints(...)]`. No runtime bug today, but mixing `constr` and `Field` constraints in the same codebase is inconsistent and `constr` may be removed in Pydantic v3.

**Fix:** No immediate action needed — this is a tech-debt note for the next schema refactor. When touching these classes for other reasons, migrate to:

```python
from typing import Annotated
from pydantic import StringConstraints

AgentName = Annotated[str, StringConstraints(min_length=1, max_length=100)]
```
