## Summary

Phase 05.1 is **not a frontend build** — it is a *contract-hardening + handoff* phase. Lovable will generate React/Vite/Tailwind/shadcn code in a separate workspace; this Python/FastAPI repo only owns three deliverables:

1. **Backend gap closure** — the approved `05.1-UI-SPEC.md` references endpoints, payload shapes, and column names that **do not yet match** the FastAPI surface shipped by Phases 1–5. Highest-impact misalignments: campaign webhooks (3 URLs in backend vs 1 + per-tool URL in UI-SPEC), `campaigns.tools` shape (object with required `webhook_url` in backend vs object without `webhook_url` in UI-SPEC), agent columns (`system_prompt/rules/tone_of_voice/faq/company_info/product_info` in backend vs `who_is_agent/company_knowledge/knowledge_base/voice_baseline/tone/...` in UI-SPEC), onboarding path naming (`/qr-start` + `/qr-status/{id}` in backend vs `/qr` + `/sessions/{id}` in UI-SPEC), and several other path/shape diffs catalogued in §1.
2. **Handoff artifact** — a `lovable-handoff/` bundle in this repo that Lovable's chat will consume verbatim: AGENTS.md/CLAUDE.md instruction file at repo root of the Lovable project (or pasted into Lovable workspace Knowledge), an `openapi.json` exported from FastAPI, a generated TypeScript client (`openapi-typescript`), a `.env.example`, screen-by-screen build order, and the existing `design-source/` bundle copied verbatim.
3. **Verification path** — telemetry ingestion endpoint + auto-validation that Lovable's deployed app + this backend hit `time_to_first_campaign_seconds < 600` and close the 7 HUMAN-UAT items.

**Primary recommendation:** Plan this phase as **4 backend plans + 1 handoff-bundle plan + 1 verification plan** (see §9). Backend plans are migration-first (raw SQL, Phase 6 in roadmap was reserved for admin bot — we are inserting Phase 05.1's data-model deltas in front of it). The handoff bundle is generated, not hand-written.

### Claude's Discretion (research these and recommend)

- **Telemetry storage backend.** UI-SPEC §9 lists 15 events. No telemetry table exists. Decide: dedicated `telemetry_events` PostgreSQL table vs. write-through to PostHog/Segment vs. log-only-to-stdout (with structured JSON parseable by Datadog later). See §4 for recommendation.
- **Supabase JWT verification algorithm.** Current code (`app/utils/auth.py`) does HS256 with shared secret. Supabase has moved to ES256 + JWKS (Oct 2025). UI-SPEC says nothing about which path. Recommend: keep HS256 in 05.1 (already working, tested), file a TODO for v2 migration. See §2.
- **OpenAPI→TypeScript generation tool.** Options: `openapi-typescript` (codegen TS types), `orval` (full client + TanStack Query hooks), hand-written zod. Recommend: `openapi-typescript` only — Lovable already generates its own TanStack Query hooks; we just need source-of-truth types. See §3.
- **Lovable handoff format.** Single master prompt vs. screen-by-screen prompts vs. AGENTS.md file vs. Lovable Knowledge field. Recommend: bundle all four — AGENTS.md drives the agent, Knowledge field carries persistent context, screen-by-screen prompts drive incremental builds. See §3.
- **Where to put the `lovable-handoff/` bundle.** New top-level directory `lovable-handoff/` (committed) — generated artifacts at every backend release.
- **CORS update strategy.** Currently a single comma-separated env var (`CORS_ALLOWED_ORIGINS`). Add Lovable preview domain pattern + production domain. See §1 row.
- **Funnel "Engaged" stage source.** UI-SPEC Sankey funnel shows Sent → Replied → **Engaged** → Lead → Handoff. Backend analytics returns sent/replied/leads/finishes — no "engaged" definition. Recommend a query: `engaged = conversations with ≥ 2 inbound messages from contact` (vs. 1 reply only).

## Project Constraints (from CLAUDE.md)

Hard rules — research must not propose anything that contradicts these. Planner should treat as non-negotiable verification gates.

1. **Объясни перед кодом.** Каждый plan MUST start with 2–3 line Russian explanation of what + why; only after user approval can task agents write code. Discuss-before-do.
2. **Async везде.** Все DB через `async/await` + `AsyncSession`. Listener / queue / workers — all asyncio. `time.sleep()` is banned (use `await asyncio.sleep()`).
3. **Migrations:** `migrations/018_phase05.1.sql` (next available number — last shipped is `017_phase5.sql`). Raw SQL only, idempotent (`CREATE TABLE IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `DROP CONSTRAINT IF EXISTS`). Wrap in `BEGIN; ... COMMIT;`. Never Alembic.
4. **No sync HTTP libraries.** `httpx` async only (already in requirements.txt). The telemetry endpoint MUST be async.
5. **No `print()`.** All output through `logging.getLogger(__name__)`. Logs must NOT contain API keys, JWT tokens, plaintext session strings, or full LLM prompts (the prompt-leak guard from Phase 5 must be preserved — see §7 verification).
6. **Empirical rate limits 4/20/150 — frozen.** UI-SPEC builder step 5 displays these as the "green corridor". No PATCH endpoint must allow lowering them in a way that breaks the contract; no UI must hide the warning.
7. **Sessions encrypted (Fernet).** Already in place; UI must never see decrypted session strings.
8. **Retry-логика FloodWait не ломается без явной просьбы.** Onboarding error handling for `FLOOD_WAIT N` must surface countdown to UI, not silently swallow.
9. **Communication = Russian, code/commits = English.** All plan files written in mixed Russian narrative + English identifiers (matches existing PLAN.md style across phases 1–5).

### Pattern 1: Migration first, ORM second, router third

Phase 5 (the closest analog) shipped migration → ORM model deltas → schema deltas → router rewrites → router register in `main.py`. Always in that order, always in one wave per concern.

```python
# Source: app/models/__init__.py (existing pattern, Phase 4 Campaign model)
class Campaign(Base):
    __tablename__ = "campaigns"

    id = Column(UUID(as_uuid=True), primary_key=True, server_default=func.gen_random_uuid())
    workspace_id = Column(UUID(as_uuid=True), ForeignKey("workspaces.id", ondelete="CASCADE"), nullable=False)
    # ... existing columns ...
    # 05.1 ADDITIONS (see §1):
    audience_hints = Column(Text, nullable=True)
    primary_goal = Column(String(20), nullable=True)  # CHECK: book_meeting|qualify|click|engage
    success_criteria = Column(Text, nullable=True)
    webhook_url = Column(Text, nullable=True)  # unified signal webhook (separate from per-tool webhook_url)
```

### Pattern 2: Workspace-scoped dependency injection (locked)

Every new router uses `Depends(auth_dep)` returning `AuthCtx(workspace_id, user_id, source, role)`. Cross-tenant access = HTTP 404 (not 403) — security pattern from Phase 1 D-04.

```python
# Source: app/routers/analytics.py (existing pattern)
@router.get("/workspace", response_model=AnalyticsCards)
async def workspace_analytics(
    ctx: AuthCtx = Depends(auth_dep),
    db: AsyncSession = Depends(get_db),
) -> AnalyticsCards:
    return await _compute_cards(db, ctx.workspace_id, scope=None)
```

### Pattern 3: Error envelope `{code, message}` (locked)

Every HTTPException uses `detail={"code": "UPPER_SNAKE_CODE", "message": "human readable"}`. UI-SPEC §6.6 (error boundaries) and §8.3 (copywriting contract) map `code` → user-friendly English string. Never display raw `message`.

```python
# Source: app/utils/auth.py
raise HTTPException(
    status_code=401,
    detail={"code": "TOKEN_EXPIRED", "message": "JWT expired"},
)
```

### Pattern 4: Telemetry write-through (NEW for this phase)

```python
# Recommended new file: app/routers/telemetry.py
class TelemetryEvent(BaseModel):
    event: str  # e.g. "magic_link_requested" — must be in UI-SPEC §9 whitelist
    props: dict[str, Any] = Field(default_factory=dict)
    client_timestamp: Optional[datetime] = None  # Lovable's clock; server overrides on insert

@router.post("/api/v1/telemetry/events", status_code=202)
async def ingest_event(
    body: TelemetryEvent,
    ctx: AuthCtx = Depends(auth_dep),
    db: AsyncSession = Depends(get_db),
):
    # Validate event name against whitelist (UI-SPEC §9)
    if body.event not in TELEMETRY_EVENT_WHITELIST:
        raise HTTPException(400, {"code": "UNKNOWN_EVENT", "message": ...})
    await db.execute(text("""
        INSERT INTO telemetry_events
            (workspace_id, user_id, event, props, client_ts, server_ts)
        VALUES (:wid, :uid, :event, :props::jsonb, :cts, NOW())
    """), {...})
    return {"accepted": True}
```

### Pattern 5: OpenAPI as contract source-of-truth

FastAPI auto-generates `/openapi.json`. The handoff bundle plan must (a) script the export, (b) diff the export against UI-SPEC §5's endpoint list in CI, (c) generate `types/api.ts` from the same JSON.

```bash
# CI script (recommended new file: scripts/export-handoff.sh)
docker compose up -d api
sleep 5
curl -s http://localhost:8000/openapi.json | jq . > lovable-handoff/openapi.json
npx -y openapi-typescript lovable-handoff/openapi.json -o lovable-handoff/types/api.ts
python scripts/check-uispec-endpoints.py lovable-handoff/openapi.json .planning/phases/05.1-lovable-ui-v1/05.1-UI-SPEC.md
```

### Anti-patterns to avoid

- **Building React components in this repo.** Lovable owns the React tree. Don't.
- **Hardcoding telemetry events in routers (e.g. "track event when X happens").** Telemetry fires from frontend; backend only records what frontend reports. Server-side derived events (e.g. `time_to_first_campaign_seconds`) come from SQL queries over the events table, not from emitting them at runtime.
- **Adding a HMAC header to the telemetry endpoint.** UI-SPEC explicitly defers HMAC signing. JWT + CORS allowlist is enough for v1.
- **Lowering the empirical rate limits (4/20/150) to "make the UI happier".** CLAUDE.md hard rule.
- **Rewriting `app/utils/auth.py` to JWKS in 05.1.** Defer to v2. The current code works against Supabase HS256 secret; migration is a 1–2 day refactor on its own.
- **Renaming endpoint paths in backend to match UI-SPEC names exactly when the backend's names are also reasonable** (e.g. `/contacts/import` is fine; UI-SPEC's `/contacts/csv-apply` was an aspirational guess). Easier to **fix UI-SPEC** to match backend than the other way around — UI-SPEC is a contract, but backend already has shipped paths used by Phase 5 tests. Recommend: **publish a single "API path reconciliation" patch to UI-SPEC** as part of the handoff bundle, and Lovable follows the reconciled paths.

## Common Pitfalls

### Pitfall 1: Treating UI-SPEC endpoint names as literal paths

**What goes wrong:** Plans add new routers under names like `/csv-preview`, `/csv-apply`, `/check-contacts`, `/senders/{id}` to match UI-SPEC verbatim — but Phase 5 tests already cover the existing names (`/contacts/import/preview`, `/contacts/import`, `/contacts/recheck`, `/senders/{slug}`). Renaming would break 94 Phase 5 tests.

**Why it happens:** UI-SPEC was written by a UI researcher reading screens, not the routers.

**How to avoid:** Treat UI-SPEC §5 "Backend:" rows as **intent**, not paths. Reconcile by patching UI-SPEC to the **shipped** path names, then regenerate the handoff bundle. Diff `lovable-handoff/openapi.json` against UI-SPEC §5 in CI to catch future drift.

**Warning signs:** Test suite goes red. PR diff renames an endpoint without ALTER TABLE on a foreign key.

### Pitfall 2: `python-jose` security migration in this phase

**What goes wrong:** Someone reads §2 and decides to swap python-jose → PyJWT during 05.1. Auth path is critical; swapping the JWT lib at the same time as widening 11 agent columns + adding telemetry + adding Lovable integration risks a launch-blocking auth regression.

**Why it happens:** "Let's clean up while we're here" instinct.

**How to avoid:** **Defer to v2.** The TODO is already in `app/utils/auth.py`. Document loudly in this RESEARCH that 05.1 leaves auth alone.

**Warning signs:** Any plan touches `app/utils/auth.py` for reasons other than CORS or new error codes.

### Pitfall 3: Supabase JWT algorithm: HS256 vs ES256 + JWKS

**What goes wrong:** Supabase changed default JWT signing algorithm from HS256 (shared secret) to ES256 + JWKS (asymmetric keys, public endpoint) around October 2025. Lovable's auto-bootstrapped Supabase project may use ES256, but our backend only supports HS256. New users hit "TOKEN_INVALID" on first login.

**Why it happens:** Default changed under us.

**How to avoid:** Two safe options:
1. **Hold legacy HS256 in Supabase project settings** — force the Lovable-created project into HS256 mode in Supabase Dashboard → Settings → API → JWT Settings → Algorithm. Document in handoff bundle setup instructions. Works today. [Supabase JWT docs](https://supabase.com/docs/guides/auth/jwts) describe both.
2. **Add ES256 fallback** — extend `_decode_supabase_jwt` to detect the `alg` header and dispatch to JWKS (with `httpx` + `pyjwt`'s `PyJWKClient` equivalent). More work; defer to v2 per Pitfall 2.

**Plan recommendation:** Option 1 in 05.1. Document in handoff bundle. File v2 TODO for option 2.

**Warning signs:** 401 TOKEN_INVALID toasts in Lovable preview right after deploy.

### Pitfall 4: Telemetry queue / loss-of-events on browser close

**What goes wrong:** `campaign_launched` event fires after POST `/campaigns/{id}/start` returns 200, but the user closes the tab before `track()` finishes the network call. Core Value KPI is undercount.

**Why it happens:** Single-shot fire-and-forget AJAX.

**How to avoid:** Frontend should use `navigator.sendBeacon()` for telemetry events on `pagehide` (Lovable-side; document in AGENTS.md). Server-side: events arrive as POST; idempotency is on UI client via `event_id` UUID generated in browser and stored as PK with ON CONFLICT DO NOTHING.

**Warning signs:** Core Value query returns lower numbers than activity logs suggest.

### Pitfall 5: Funnel "Engaged" stage definition drift

**What goes wrong:** Dashboard funnel "Engaged" between Replied and Lead. Without an explicit definition, three engineers will write three queries (≥2 inbound; ≥1 inbound + ≥1 outbound; conversation duration ≥X minutes). Numbers change every commit.

**Why it happens:** UI-SPEC §5.3 names the stages but doesn't formally define "Engaged".

**How to avoid:** **Define in this RESEARCH:** `engaged = COUNT(DISTINCT conversation_id WHERE inbound_message_count >= 2 AND status NOT IN ('lead','handoff','finished','bot_ignored'))`. Lock in plan. Document in `lovable-handoff/AGENTS.md`.

**Warning signs:** Stage counts in funnel don't sum monotonically (replied ≥ engaged ≥ lead ≥ handoff).

### Pitfall 6: Campaign `tools` migration drops Phase 4 tests

**What goes wrong:** Changing `tools` shape from `[{name, description, parameters, webhook_url, webhook_method}]` to `[{id, name, description, parameters}]` (drop webhook_url) breaks `tests/test_custom_tools_wiring.py` and `tests/test_campaign_webhooks.py`. Phase 4 ships, Phase 05.1 PR turns red.

**Why it happens:** UI-SPEC §10 was written without checking shipping tests.

**How to avoid:** Migration must be backwards-compatible: keep `webhook_url` as **deprecated optional** field on the Pydantic schema for one release cycle. ai_engine reads `coalesce(campaign.webhook_url, tool.webhook_url)`. Phase 4 tests still pass. Mark `tool.webhook_url` as `deprecated=True` in OpenAPI so Lovable doesn't surface it.

**Warning signs:** `test_custom_tools_wiring.py` fails because tool schema rejects `webhook_url`.

### Pitfall 7: CORS `allow_origin_regex` vs `allow_origins`

**What goes wrong:** `CORSMiddleware(allow_origins=["https://*.lovableproject.com"])` — **wildcards in `allow_origins` don't work.** Returns 0 origins matched, browser blocks all Lovable preview deploys.

**Why it happens:** Starlette/FastAPI only does literal string match in `allow_origins`.

**How to avoid:** Use `allow_origin_regex=r"https://.*\.lovableproject\.com$"` (and add a separate static list for prod). Verify with `curl -H "Origin: https://abc-123.lovableproject.com" -H "Access-Control-Request-Method: POST" -X OPTIONS http://localhost:8000/api/v1/auth/me -i`.

**Warning signs:** Lovable preview shows "CORS error" in console; backend logs show "OPTIONS preflight rejected".

### Pitfall 8: Lovable rewrites the API shape on every Knowledge edit

**What goes wrong:** Lovable's agent reads Knowledge + AGENTS.md, sees a description like "the agent fetches /agents and renders a 2-tab editor", and **invents a 2-tab shape that doesn't match the backend response.** Components are built against imagined types.

**Why it happens:** Lovable agent is generative — it fills gaps with plausible guesses.

**How to avoid:** **Ship `lovable-handoff/types/api.ts` as the type contract.** Tell Lovable in AGENTS.md: "Import types from `@/types/api.ts` — these are generated from the backend OpenAPI spec. Never invent your own types for `/api/v1/*` responses." Lovable will follow concrete imports more reliably than prose descriptions.

**Warning signs:** Lovable preview renders fields that don't exist in API responses (or vice versa).

### Pitfall 9: Empirical rate limits become a UI-side concern (regression risk)

**What goes wrong:** Builder step 5 (UI-SPEC §5.5) shows the green corridor `4 / 20 / 150`. A well-meaning Lovable build adds a "Customize for high-volume campaigns" toggle that proposes 10/50/500. CLAUDE.md hard rule violated.

**Why it happens:** UI feature creep.

**How to avoid:** AGENTS.md must say: **"The 4/20/150 limits are not configurable in v1. Never offer a UI control to change them. They are a hard backend constraint per CLAUDE.md."**

**Warning signs:** PR adds a number input bound to `rate_per_min` / `rate_per_hour` / `rate_per_day` on the campaign builder.

### Pitfall 10: Privacy / data-residency for external first customer

**What goes wrong:** First external customer is no longer AGS Foods (internal). Their leads (names, phones) live in our DB. GDPR/CCPA right-to-erasure flow doesn't exist. Onboarding survey question.

**Why it happens:** Brownfield internal tool going external.

**How to avoid:** **Out of scope for 05.1 build,** but the customer-facing settings page (UI-SPEC §5.11) should include a link "Request data export / deletion" → mailto for now. Document in Open Questions. Real GDPR flow = v1.1.

**Warning signs:** Customer asks for data deletion and we have to do it manually.

### Example 1: Telemetry event ingest endpoint (NEW pattern for this phase)

```python
# app/routers/telemetry.py — NEW
"""Telemetry router (Phase 05.1).

Ingest UI events for Core Value KPI tracking. JWT-only (no API key path —
events are user-context, not integration-context).

Storage = local Postgres table `telemetry_events`. NO PostHog/Segment in v1.
"""
import logging
from datetime import datetime
from typing import Any, Optional
from uuid import UUID, uuid4

from fastapi import APIRouter, Depends, HTTPException
from pydantic import BaseModel, Field
from sqlalchemy import text
from sqlalchemy.ext.asyncio import AsyncSession

from app.database import get_db
from app.utils.auth import AuthCtx, auth_dep

logger = logging.getLogger(__name__)
router = APIRouter(prefix="/api/v1/telemetry", tags=["telemetry"])

# UI-SPEC §9 — 15 events. Whitelist enforced at ingest time.
_EVENT_WHITELIST = {
    "magic_link_requested", "signup_completed", "sender_added",
    "contacts_imported", "csv_import_completed", "agent_created",
    "campaign_created", "campaign_launched", "campaign_paused",
    "campaign_resumed", "conversation_taken_over_by_human",
    "llm_trace_opened", "workspace_api_key_created", "settings_changed",
    "agent_voice_changed", "custom_tool_added", "dashboard_viewed",
}


class TelemetryEventIn(BaseModel):
    event_id: Optional[UUID] = Field(default_factory=uuid4)  # client-supplied for idempotency
    event: str = Field(..., min_length=1, max_length=80)
    props: dict[str, Any] = Field(default_factory=dict)
    client_timestamp: Optional[datetime] = None


class CoreValueResponse(BaseModel):
    time_to_first_campaign_seconds: Optional[int] = None
    signup_at: Optional[datetime] = None
    first_launch_at: Optional[datetime] = None


@router.post("/events", status_code=202)
async def ingest_event(
    body: TelemetryEventIn,
    ctx: AuthCtx = Depends(auth_dep),
    db: AsyncSession = Depends(get_db),
):
    if body.event not in _EVENT_WHITELIST:
        raise HTTPException(
            status_code=400,
            detail={"code": "UNKNOWN_EVENT",
                    "message": f"Event '{body.event}' not in whitelist"},
        )
    await db.execute(text("""
        INSERT INTO telemetry_events
            (event_id, workspace_id, user_id, event, props, client_ts, server_ts)
        VALUES (:eid, :wid, :uid, :event, :props::jsonb, :cts, NOW())
        ON CONFLICT (event_id) DO NOTHING
    """), {
        "eid": str(body.event_id),
        "wid": str(ctx.workspace_id),
        "uid": ctx.user_id,
        "event": body.event,
        "props": body.props,
        "cts": body.client_timestamp,
    })
    await db.commit()
    return {"accepted": True, "event_id": str(body.event_id)}


@router.get("/core-value", response_model=CoreValueResponse)
async def core_value(
    ctx: AuthCtx = Depends(auth_dep),
    db: AsyncSession = Depends(get_db),
):
    """Computes time_to_first_campaign_seconds — UI-SPEC §9 KPI #9."""
    row = (await db.execute(text("""
        SELECT
            (SELECT MIN(server_ts) FROM telemetry_events
                WHERE workspace_id = :wid AND event = 'signup_completed') AS signup_at,
            (SELECT MIN(server_ts) FROM telemetry_events
                WHERE workspace_id = :wid AND event = 'campaign_launched') AS first_launch_at
    """), {"wid": str(ctx.workspace_id)})).first()
    delta_seconds = None
    if row.signup_at and row.first_launch_at:
        delta_seconds = int((row.first_launch_at - row.signup_at).total_seconds())
    return CoreValueResponse(
        time_to_first_campaign_seconds=delta_seconds,
        signup_at=row.signup_at,
        first_launch_at=row.first_launch_at,
    )
```

## Telemetry Architecture (Core Value KPI)

UI-SPEC §9 lists 15 frontend events. Storage and computation must be in this backend.

### Event flow

```
Lovable browser              FastAPI                   PostgreSQL
─────────────────            ────────                  ──────────
1. User signs up
2. `track('signup_completed', ...)`  →  POST /api/v1/telemetry/events  →  INSERT INTO telemetry_events
                                       (auth: Bearer JWT)               (event_id PK, ON CONFLICT DO NOTHING)
                                       returns 202 Accepted
...
N. User clicks "Launch campaign"
N+1. `track('campaign_launched', ...)`  →  POST /api/v1/telemetry/events
...
Lovable Settings page         GET /api/v1/telemetry/core-value
                              →  SELECT MIN(signup), MIN(launch) WHERE workspace_id=...
                              →  delta_seconds = MIN(launch) - MIN(signup)
                              →  return {time_to_first_campaign_seconds, signup_at, first_launch_at}
```

### Why not PostHog / Segment in v1

- Adds external dependency to Lovable's build (env var, SDK init, network egress)
- 30-min integration time per Lovable project — slows Core Value validation
- Core Value KPI is a single 2-line SQL query — overkill for SaaS provider
- v2: migrate when we need cohort analysis or funnel visualization beyond Sankey

### Why not log-only-to-stdout

- Can't compute `time_to_first_campaign_seconds` over arbitrary lookback without re-parsing logs
- Datadog/Logtail ingest is another paid SaaS
- DB persistence is free; query is fast; no scaling concern in v1

### Storage shape (matches Example 2 migration)

```sql
CREATE TABLE telemetry_events (
    event_id      UUID PRIMARY KEY,                       -- client-supplied for idempotency
    workspace_id  UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    user_id       TEXT,                                   -- supabase 'sub'
    event         VARCHAR(80) NOT NULL,                   -- whitelist-validated
    props         JSONB NOT NULL DEFAULT '{}'::jsonb,
    client_ts     TIMESTAMPTZ,                            -- browser clock (display only)
    server_ts     TIMESTAMPTZ NOT NULL DEFAULT NOW()      -- authoritative; used in queries
);
CREATE INDEX idx_telemetry_workspace_event_server
    ON telemetry_events(workspace_id, event, server_ts DESC);
```

### Core Value query

```sql
WITH t AS (
  SELECT
    (SELECT MIN(server_ts) FROM telemetry_events
       WHERE workspace_id = $1 AND event = 'signup_completed') AS signup_at,
    (SELECT MIN(server_ts) FROM telemetry_events
       WHERE workspace_id = $1 AND event = 'campaign_launched') AS first_launch_at
)
SELECT
  signup_at,
  first_launch_at,
  EXTRACT(EPOCH FROM (first_launch_at - signup_at))::INT AS time_to_first_campaign_seconds
FROM t;
```

## State of the Art

| Old approach | Current approach (2025–2026) | When changed | Impact for this phase |
|--------------|------------------------------|--------------|----------------------|
| Supabase HS256 JWT (shared secret) | Supabase ES256 JWT + JWKS (asymmetric, public discovery) | Oct 2025 | Pin Lovable's Supabase project to HS256; defer ES256 to v2 (Pitfall 3) |
| `python-jose` for JWT | `PyJWT` | 2023+ (jose abandoned 2021) | Document deferral; don't migrate in 05.1 (Pitfall 2) |
| Hand-written TypeScript types | `openapi-typescript` generated from `/openapi.json` | 2023+ | Standard for this phase ([Source](https://supabase.com/docs/guides/api/rest/generating-types)) |
| Single Lovable system prompt at chat start | AGENTS.md root file (always-read) + per-screen prompts | 2025+ | Standard for this phase ([Lovable Best Practices](https://www.closefuture.io/blogs/best-practices-for-lovable-app-development)) |
| Lovable hand-built TanStack Query hooks | Lovable auto-generates Query hooks from typed responses | 2025+ | Means we don't need orval — types-only is enough |
| Backend emits telemetry events | Frontend emits, backend ingests | 2024+ | Right model for Core Value KPI |
| OpenAPI 3.0 | FastAPI 0.109 emits OpenAPI 3.1 | Late 2023 | openapi-typescript 7.x supports 3.1 natively |

**Deprecated / outdated patterns:**
- `python-jose` — unmaintained since 2021, known `ecdsa` vuln, FastAPI docs are dropping the recommendation
- Single shared JWT secret — Supabase moving away from it; OK for v1 but flag for v2
- Hand-rolled `track()` with bare `fetch()` — use `navigator.sendBeacon()` on `pagehide` for reliability

   - What we know: UI-SPEC §5.5 builder step 5 says "aimly enforces 4 / 20 / 150" — hardcoded copy.
   - What's unclear: If we ever raise the limits, do we want UI to auto-update or do we re-deploy UI?
   - Recommendation: For v1 — hardcoded UI string is fine. Document in AGENTS.md that changing the limits requires a coordinated frontend+backend deploy.

4. **Does the GDPR/data-export flow block first external customer?**
   - What we know: First customer is external, not internal AGS Foods.
   - What's unclear: Are they EU-based? Will the contract require formal data export?
   - Recommendation: Out of scope for 05.1 build; mailto link in settings as placeholder; v1.1 if customer asks.

5. **Should reconciliation patches to UI-SPEC.md be committed as a `UI-SPEC.diff` in the handoff bundle, or as an edit to UI-SPEC itself?**
   - What we know: UI-SPEC is "approved", changing it mid-stream is risky.
   - What's unclear: Whether the planner / checker re-runs gate-checks on edits.
   - Recommendation: **Edit UI-SPEC directly** with a clear changelog entry at the bottom ("2026-05-23: API path reconciliation — see §5 row notes"). UI-SPEC is a living contract; that's why GSD has phase-internal artifacts.

6. **Where do Lovable preview deployments get their `VITE_BACKEND_URL`?**
   - What we know: Lovable preview URLs are auto-generated; each preview can have different env vars.
   - What's unclear: Does Lovable expose a per-branch env var workflow?
   - Recommendation: Document in handoff bundle `.env.example`: dev = `http://localhost:8000`, staging = `https://staging.aimly.com`, prod = `https://api.aimly.com`. Lovable's project settings → env vars panel.

### Wave 2 — Endpoints (parallel after Wave 1)

**Plan 05.1-03: Campaign + agent + sender endpoint gap fixes** [Wave 2, depends_on: 05.1-01]

**Plan 05.1-04: Analytics endpoints + telemetry router** [Wave 2, depends_on: 05.1-01]

*Closes:* UI-DASH-01, UI-CAMPD-01, UI-TEL-01, UI-TEL-02.

### Wave 3 — Integration (sequential after Wave 2)

**Plan 05.1-05: Lovable handoff bundle generation** [Wave 3, depends_on: 05.1-03, 05.1-04]
*Objective:* Create `lovable-handoff/` directory. Write AGENTS.md, KNOWLEDGE.md, screen-build-order.md, error-codes.md, telemetry-events.md, README.md. Add `scripts/export-handoff.sh` + `scripts/check-uispec-endpoints.py`. Patch UI-SPEC for path reconciliation (see §1 ⚠ rows). Commit `openapi.json` + `types/api.ts`.
