## Decisions Made

See `key-decisions:` in frontmatter for the canonical list. Highlights:

1. **auto_pause_triggers + max_message_length resurrection** — these two columns were intentionally dropped by Phase 3 migration 015 because Phase 3 considered them "campaign concerns". UI-SPEC §5.8 puts them squarely back in agent-level settings (the agent's voice limits + ban-list-style triggers). Migration 018 adds them back as nullable; `ADD COLUMN IF NOT EXISTS` is safe on both fresh DBs (real ADD) and any prod DB that managed to skip 015 (no-op).
2. **ToolSpec.webhook_url Optional + id field added** — UI-SPEC §10 specifies tools as `{id, name, description, parameters}` with no per-tool webhook (campaign-level webhook_url handles dispatch). Phase 4 test_custom_tools_wiring.py still passes dicts with per-tool webhook_url, so the field stays Optional rather than being removed (Pitfall 6 from RESEARCH.md).
3. **CampaignResponse uses `Optional[str]` for v2 webhook_url** — matches how the existing lead/handoff/finish_webhook_url fields are typed in CampaignResponse (DB-passthrough, not re-validated HttpUrl). CampaignCreate/Update use `Optional[HttpUrl]` for client-side validation only.
4. **AgentResponse.tone is `Optional[dict]`, not `Optional[ToneSpec]`** — pre-05.1 rows in production have NULL tone; from_attributes=True ORM round-trip cannot re-validate the response payload against ToneSpec without a server-default backfill. Plain dict gives back-compat with NULL.
5. **telemetry_events.event_id is client-supplied PK** — UI uses navigator.sendBeacon which retries on flaky networks; making event_id a server-default UUID would create duplicate rows on retry. Client supplies UUIDv4 per event so PK collision dedups retries.

### Reality check: auto_pause_triggers status after migration 015

The plan's Task 1 `<action>` block describes `ALTER TABLE ai_contexts ADD COLUMN IF NOT EXISTS auto_pause_triggers TEXT[]` as a "defensive ADD (likely exists from pre-Phase-3, IF NOT EXISTS makes it a no-op)". Reading migration 015 (line 12) confirmed `ALTER TABLE ai_contexts DROP COLUMN IF EXISTS auto_pause_triggers;` actually drops this column during Phase 3 cleanup. So migration 018's ADD is **NOT** a no-op on fresh DBs — it's a real recreation. The migration SQL was authored to handle both cases idempotently (IF NOT EXISTS), but the SQL comment and ORM comment were both updated to document the resurrection accurately (the plan's wording would have misled a future maintainer).

This was not a code change — only a docstring/comment refinement — so it does not warrant a separate deviation entry. Documenting here so the PROJECT.md decision log can pick up the "max_message_length + auto_pause_triggers resurrected in Phase 05.1" fact.
