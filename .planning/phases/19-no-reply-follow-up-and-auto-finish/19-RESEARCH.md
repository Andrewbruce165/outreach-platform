## User Constraints (from CONTEXT.md)

### Locked Decisions (D-01..D-17 — copied verbatim)

**No-reply state semantics**
- **D-01:** `no_reply` becomes a new `Conversation.status` value — extend the CHECK constraint (`active|manual|paused|lead|handoff|finished` + `no_reply`). Visible in inbox filters and analytics via the existing status mechanism.
- **D-02:** A conversation flips to `no_reply` only after the first ping interval elapses without an incoming message — NOT immediately after the opener. Status flip and first ping fire off the same timer expiry.
- **D-03:** Any incoming message from the contact returns the conversation to `active` and cancels all scheduled pings for it.
- **D-04:** Silence timer counts from the **last outgoing message** (opener, AI reply, or previous ping). Each ping restarts the timer for the next one.

**Follow-up scope (who gets pinged)**
- **D-05:** Pings cover **all silent dialogs**, both kinds: (a) contact never replied to the opener, and (b) contact replied earlier but went silent mid-dialog. User explicitly chose the wider scope over never-replied-only.
- **D-06:** Only conversations with `status='active'` are eligible for pings (plus `no_reply` itself once flipped). `lead`, `handoff`, `manual`, `paused`, `finished` are NEVER pinged.

**Ping content**
- **D-07:** Ping text is **AI-generated by the campaign's agent** with full dialog history in context. Reuses the existing ai_engine/prompt-assembly infrastructure; goes through the campaign's configured LLM provider (Phase 18).
- **D-08:** Max pings before auto-finish is a **configurable field in the campaign form** (default 2, bounds 1–5). Auto-finish also fires on the time threshold — whichever comes first.

**Auto-finish behavior**
- **D-09:** On auto-finish: conversation → `status='finished'`, all scheduled pings cancelled, existing `finish_webhook_url` fired (if configured) with a `no_reply` reason marker.
- **D-10:** Auto-finish N hours counts from the **last outgoing message** (same anchor as the ping timer).
- **D-11:** Auto-finished contacts are eligible for re-contact **by the existing rules** (`allow_recontact` + `recontact_min_age_days`, Phase 9/migration 026). No changes needed.

**Scheduler & limits**
- **D-12:** Both settings are expressed in **hours**: ping interval (default 24, bounds 4–168) and auto-finish threshold (default 72, bounds 24–720). Follow Up toggle defaults to OFF.
- **D-13:** Pings are delivered **through message_queue as follow-up items**: campaign working hours and per-sender rate limits (4/min, 20/h, 150/day) fully apply; the daily new-dialog cap and pacing do NOT block them (PACE-07 / Phase 12 semantics). Interval expiring at night → ping goes out next working-hours window.
- **D-14:** Ping must come from the **same sender account** that owns the conversation. If frozen/restricted, the ping waits for it to recover; if auto-finish arrives first, the conversation just closes. No failover.

**Toggle lifecycle on running campaigns**
- **D-15:** Enabling the toggle on an already-running campaign applies **retroactively with smoothing**: existing silent dialogs also get pings, queue + rate limits spread the wave. Dialogs already past the auto-finish threshold at enable time are finished immediately, without pings.
- **D-16:** Campaign `paused` **freezes everything**: no pings sent AND auto-finish timers do not fire while paused; resume continues. Campaign `done` → all scheduled pings cancelled permanently.

**Races & edge cases**
- **D-17:** An incoming message from the contact **cancels any pending ping** in the queue. Double protection: the listener cancels on receipt AND the queue worker re-checks "has the contact replied since this ping was scheduled?" right before sending.

## Summary

Phase 19 is entirely a **brownfield extension of existing mechanisms** — zero new libraries. Every capability maps to a pattern already proven in this codebase:

1. A **timer-driven state machine** over `conversations`, evaluated by a new dedicated Postgres-polling background worker that is a near-copy of `CampaignEnqueueWorker` / `ContactCheckWorker` (asyncio task, tick loop, `FOR UPDATE SKIP LOCKED`, registered in `main.py` lifespan).
2. **Ping delivery through `message_queue`**, which already treats "a prior `sent` item to the same phone in the same campaign" as a follow-up that bypasses the new-dialog cap and pacing but obeys working hours + rate limits — pings are follow-ups *by construction*, requiring **no changes to throttling logic**.
3. **AI ping text generated at send time** via a new `TelegramListenerService`-independent path that reuses `ai_engine`'s prompt-assembly + Phase 18 provider resolution. This is critical: the queue snapshots rendered text at enqueue, and a canned or stale-at-enqueue ping would be wrong. Generate the ping just-before-send, OR (cleaner) generate at scheduling time inside the worker tick immediately before enqueue — but re-check "replied since?" first (D-17 second guard is what makes either safe).
4. **Cancel-on-reply** hooks the existing `handle_incoming_message` path in the listener, which today does NOT revert status or cancel queue items — this is the one genuinely new listener behavior.

**Primary recommendation:** Add one migration (extend `conversations.status` CHECK + add ping-state columns to `conversations` + 4 campaign columns), one new `FollowUpWorker` service modeled on `CampaignEnqueueWorker`, a ping-generation helper reusing `ai_engine`, a listener hook for revert+cancel, a pre-send re-check in `queue.py`, campaign schema/router fields following the `max_new_dialogs_per_day` pattern, and the `no_reply` reason marker in `webhook_notify.notify_signal`. Do NOT touch the empirical rate-limit intervals.

### Pattern 1: Dedicated `FollowUpWorker` (RECOMMENDED over piggyback)
**What:** A new background worker, structurally a copy of `CampaignEnqueueWorker` (`app/services/campaign_enqueue.py:46-112`): `__init__` reads a `poll_interval` from settings, `start()` spawns `asyncio.create_task(self._run())`, `_run()` loops `await self._tick()` + `await asyncio.sleep(poll_interval)` with a broad `except` that never lets the loop die, `stop()` cancels + awaits.

**Why dedicated, not piggyback on queue worker:**
- The queue worker's `_process_next_for_sender` is per-sender and gated by the untouchable rate-limit machinery; timer evaluation is per-conversation and independent. Mixing them risks touching protected code.
- `CampaignEnqueueWorker` already establishes the "campaign-scoped background sweep" precedent — a follow-up sweep is the same shape.
- Isolation matches the project's worker-per-concern convention (queue / warmup / onboarding-cleanup / contact-check / campaign-enqueue / kb-ingest are all separate).

**Tick responsibilities (one pass over eligible conversations):**
1. `JOIN conversations → campaigns` where `campaigns.follow_up_enabled = true` AND `campaigns.status = 'running'` (D-16: skip `paused`/`done`; done also triggers ping-cancel — do that in the lifecycle endpoint, not the tick).
2. Eligible conversation states: `status IN ('active','no_reply')` (D-06); exclude `lead/handoff/manual/paused/finished`.
3. Compute `last_outbound_at` = MAX(`messages.created_at` WHERE `direction='outbound'`) for the conversation (D-04/D-10 anchor). Store it as a column (Pattern 2) to avoid re-aggregating every tick.
4. **Auto-finish check first** (D-08 "whichever comes first"): if `NOW() - last_outbound_at >= auto_finish_hours` OR `pings_sent >= follow_up_max_pings` → flip `status='finished'`, cancel pending ping queue items for this conversation, fire finish webhook w/ `reason='no_reply'` (D-09). D-15: on toggle-enable, already-past-threshold dialogs hit this branch immediately.
5. **Ping check:** else if `NOW() - last_outbound_at >= follow_up_interval_hours` AND `pings_sent < follow_up_max_pings` → flip `status='no_reply'` (D-02, only from `active`; `no_reply` stays), generate ping text (Pattern 4), `enqueue_message(...)` with the owning sender + campaign (D-13/D-14), increment `pings_sent`, set `last_outbound_at` forward is NOT done here — it advances naturally when the ping actually sends and writes an outbound `messages` row. **Guard against double-enqueue:** track `next_ping_due_at` / a `ping_pending` flag so the tick doesn't enqueue a second ping while one is still queued (Pattern 2).
6. Use `FOR UPDATE SKIP LOCKED` on the conversation rows claimed per tick (horizontal-scale safety, same as every other worker).

**Config knob:** add `follow_up_tick_seconds` to `app/config.py` (mirror `campaign_enqueue_tick_seconds`, default e.g. 300 — a 5-min tick is fine given interval bounds are in hours).

### Pattern 2: Ping-state columns ON `conversations` (RECOMMENDED over separate table)
**What:** Add to `conversations`:
- `pings_sent INT NOT NULL DEFAULT 0` (D-08 counter)
- `last_outbound_at TIMESTAMPTZ NULL` (D-04/D-10 timer anchor; NULL until first outbound)
- `next_ping_due_at TIMESTAMPTZ NULL` (optional but recommended — lets the tick SELECT be a cheap indexed `WHERE next_ping_due_at <= NOW()` instead of recomputing intervals for every row; also serves as the "ping already scheduled, don't double-enqueue" signal when set to NULL after enqueue and recomputed on send).

**Why columns not a table:** the state is strictly 1:1 with a conversation, cheap, and read on every tick; a join table adds no value. Precedent: `paused_at`/`paused_reason` are already conversation columns. The counter mirrors `campaigns.max_new_dialogs_per_day` living as a column.

**Where `last_outbound_at` gets written:** it must advance every time an outbound message is sent (opener, AI reply, ping). Cleanest: update it in `queue.py::_upsert_conversation` (already runs after a successful send, `app/services/queue.py:1210`) and in `listener.py::save_message` for `direction='outbound'` AI replies. Alternatively, derive it lazily in the tick via `MAX(messages.created_at)` — simpler to implement, slightly heavier per tick. **Recommendation: derive lazily in the tick for v1** (correctness over micro-optimization; interval is hours, tick is minutes, row counts are modest), and only add the stored column if profiling shows a problem. This avoids scattering writes across three send paths.

### Pattern 3: Campaign form fields (copy `max_new_dialogs_per_day`)

- `follow_up_enabled BOOLEAN NOT NULL DEFAULT false`

- `follow_up_max_pings INT NOT NULL DEFAULT 2` (bounds 1–5)

No soft-cap `warnings[]` needed unless the planner wants a "green corridor" warning (the pattern exists via `_validate_max_new_dialogs`/`WarningItem` if desired, but CONTEXT.md doesn't request one — these are hard bounds).

### Pattern 4: AI ping-text generation (reuse ai_engine, generate at send/schedule time)
**What:** `generate_response` (`ai_engine.py:1318`) is the full answerer path — it resolves campaign+agent context, provider (Phase 18), history, tools, and returns text. For a ping we want the *same prompt assembly and provider* but a proactive "no reply — nudge the contact" instruction instead of a reply to an inbound message.

**Recommended approach:** add a thin `generate_followup_ping(session, conversation_id)` to `ai_engine` that:
1. Calls `get_context_for_conversation(conversation_id, session)` (campaign+agent+provider config) and `get_conversation_history(session, conversation_id, limit=20)` — both already exist.
2. Builds the system prompt via `build_system_prompt` (unchanged) and appends a follow-up directive as the final user/system turn (e.g. "The contact has not replied for {interval}h. Send a short, natural, on-topic nudge — do not repeat the opener verbatim; reference the dialog so far if any."). Exact wording is Claude's discretion (CONTEXT.md).
3. Resolves the provider via `resolve_llm_config` (same as `generate_response`) so pings honor the campaign's Phase 18 provider/model/key (D-07).
4. Returns text only — **no tools** (a ping never triggers lead/handoff/finish signals).

**CRITICAL timing (memory: queue-snapshots-template-at-enqueue):** `message_queue` stores the rendered text at enqueue and never re-runs the LLM. So the ping text must be generated **fresh, immediately before it goes into the queue**, and the D-17 second guard ("replied since scheduled?") must run **at send time** so a reply arriving between enqueue and send suppresses a now-stale ping. Two viable placements:
- **(a) Generate in the FollowUpWorker tick, then enqueue** (text is snapshotted). Relies entirely on the queue pre-send guard (Pattern 6) to catch a reply-in-flight. Simpler.
- **(b) Enqueue a placeholder + generate at send time.** More faithful to "generate at send" but requires the queue send path to call the LLM, which it currently never does — larger blast radius on the protected send path.
- **Recommendation: (a)** — generate in the tick right before `enqueue_message`, and rely on the listener cancel (D-3) + the pre-send re-check (D-17 guard) to nullify a ping that was overtaken by a reply. The interval is hours; the enqueue→send lag is minutes; the double guard covers it.

### Pattern 5: Cancel-on-reply listener hook (D-03/D-17 — the one genuinely new listener behavior)
**What:** `handle_incoming_message` (`app/services/listener.py:698`) currently, on a genuine contact message, calls `get_or_create_conversation` and dispatches to the AI buffer — it does **NOT** revert status or cancel queue items. Add, right after the conversation is fetched (around line 933, before the AI-buffer dispatch that checks `conv["status"] == "active"`):
1. If `conv["status"] == 'no_reply'` → `UPDATE conversations SET status='active' WHERE id=...` (D-03). (This also makes the existing `if conv["ai_enabled"] and conv["status"] == "active"` AI-dispatch fire, since the normal answerer should handle the reply — but note `conv` was read before the update, so either re-read status or set the local dict.)
2. **Cancel pending pings** for this conversation: `UPDATE message_queue SET status='cancelled', error_message='contact replied' WHERE ... AND status='pending'` scoped to this sender+campaign+recipient_phone (D-17 first guard). `QueueItemStatus.cancelled` already exists in the enum (`app/models/__init__.py:22`).

**Precedent for cancelling queue items from the listener:** `_handle_antispam_signal` (listener ~1081) already pauses/cancels a sender's pending queue items — the SQL-UPDATE-from-listener pattern is established.

### Pattern 6: Pre-send "replied since scheduled?" re-check (D-17 second guard)
**What:** In `queue.py::__send_item_inner`, there is already a **pre-send guard block** (`app/services/queue.py:720-791`, "Phase 5 D-04 / Pitfall 6") that does exactly one extra SELECT on `conversations` and skips the send if `ai_enabled=false`. Add a sibling check *only for follow-up/ping items*: if the contact has an inbound `messages` row newer than this ping's `created_at` (or the conversation is no longer in `active`/`no_reply`), mark the item `cancelled` and skip. This is a single extra SELECT — consistent with the existing guard and the CLAUDE.md rule (no touching intervals, only SELECT+UPDATE on the queue item).

**How to distinguish a ping from a normal item:** the queue has no `is_followup` column. Options: (a) tag pings via `extra_data` JSONB (e.g. `{"kind": "followup"}`) at enqueue — cleanest, no migration; (b) run the reply-since check for all campaign items (harmless for openers since they have no prior inbound). **Recommendation: (a)** — set `extra_data={"kind":"followup"}` in the FollowUpWorker enqueue call and gate the extra guard on it.

### Pattern 7: Frontend + openapi regen (cross-repo)
**What:** After schema changes, regenerate `lovable-handoff/openapi.json` (offline via `app.openapi()` in the test container — Phase 16/18 precedent, no un-gated prod deploy) and add the Follow Up block to the campaign create/edit form in the sibling repo `/root/apps/aimly/aimly-tg-outreach`. UI placement fits the existing settings block alongside `recontact` / `max_new_dialogs_per_day` (Claude's discretion). This is a human-verify / cross-repo task (mirror Phase 12-04, 18-05).

### Anti-Patterns to Avoid
- **Do NOT** add a numeric floor/override to the queue's rate-limit intervals to "speed up" pings — D-13 says pings ride the existing limits. The follow-up predicate already exempts them from the cap/pacing ceiling; that is the only exemption allowed.
- **Do NOT** generate ping text at enqueue and let it sit for hours (stale). Generate immediately before enqueue and rely on the double guard, or the ping may reference a now-answered dialog.
- **Do NOT** use SQLEnum / PG `ALTER TYPE ADD VALUE` for the `no_reply` status — the table uses VARCHAR+CHECK precisely because `ALTER TYPE ADD VALUE` can't run in a transaction (AUDIT Q6, mig 016/017). Extend the CHECK with a `DO $$ … EXCEPTION $$` idempotent block.
- **Do NOT** flip to `no_reply` immediately after the opener (D-02) — only after the first interval elapses.
- **Do NOT** flip `finished`→something or ping `finished`/`lead`/`handoff`/`manual`/`paused` (D-06).

## Common Pitfalls

### Pitfall 1: Follow-up classification is implicit (SQL predicate, not a flag)
**What goes wrong:** Assuming there's an `item_type='follow_up'` — there isn't. `QueueItemType` is only `message`/`file`. "Follow-up" is derived at pick time by `EXISTS(prior sent row to same phone in same campaign)` (`queue.py:461-468`). A ping to a contact who already got an opener **is automatically a follow-up** and correctly bypasses the cap/pacing.
**Why it happens:** the CONTEXT.md language "follow-up items" suggests a discrete type; the code models it relationally.
**How to avoid:** rely on the existing predicate — the ping just needs a prior `sent` row for the same `(campaign_id, recipient_phone)`, which every silent dialog has (the opener). No new item type. Use `extra_data={"kind":"followup"}` only to gate the D-17 pre-send re-check, not for pacing classification.

### Pitfall 2: ORM `server_default` drift on the new NOT NULL columns
**What goes wrong:** Adding `pings_sent INT NOT NULL DEFAULT 0` in SQL but only `default=0` in the ORM → after a `create_all` rebuild the prod column has no DB default → any raw INSERT/UPDATE omitting it hits NotNullViolation (exactly the mig 040/042 incidents in memory).
**How to avoid:** every new NOT NULL column gets `server_default=text("0")` / `server_default="false"` in the ORM matching the migration DEFAULT.

### Pitfall 3: Ping generated stale (queue snapshots text)
**What goes wrong:** Generate ping text, sit in queue for hours, contact replies, ping still sends referencing a dead thread. (Memory: queue-snapshots-template-at-enqueue.)
**How to avoid:** the D-17 double guard (listener cancel on reply + pre-send "replied since scheduled?" re-check) is mandatory, not optional. Generate the text as late as practical (in the tick just before enqueue).

### Pitfall 4: `no_reply` breaks the AI-dispatch condition in the listener
**What goes wrong:** The listener only dispatches to AI when `conv["status"] == "active"` (`listener.py:953`). A `no_reply` conversation that receives a reply must first be reverted to `active` **before** that check, or the contact's reply is saved but the AI never answers.
**How to avoid:** revert `no_reply`→`active` and update the local `conv["status"]` (or re-read) before the `if conv["ai_enabled"] and conv["status"] == "active"` branch.

### Pitfall 5: Paused/done campaign timers (D-16)
**What goes wrong:** A paused campaign's conversations keep accruing silence time; on resume, everything auto-finishes at once, or pings burst.
**How to avoid:** the FollowUpWorker tick JOINs `campaigns.status='running'` — paused/done campaigns are simply not evaluated (timers effectively freeze because nothing acts on them). D-16 "resume continues" is satisfied because the anchor is `last_outbound_at`, which doesn't advance while paused; **but** note the silence *elapsed while paused* still counts against the wall clock. If strict "timers do not fire while paused" means elapsed-during-pause must be excluded, the planner must decide whether to shift `last_outbound_at` forward by the pause duration on resume. **Open Question 1.** For `done`: cancel pending pings in the campaign lifecycle `done` endpoint (not the tick).

### Pitfall 6: Same-sender-only when frozen (D-14)
**What goes wrong:** Enqueuing a ping to a frozen/restricted sender's queue — the queue's own `__send_item_inner` already fails items when `lifecycle_status != 'active'` or `auth_status != 'ok'` (`queue.py:712`), which would prematurely fail the ping instead of waiting.
**How to avoid:** enqueue the ping to the owning sender (D-14); if the sender is restricted, the ping should *wait*, not fail. Either don't enqueue while the sender is restricted (let the next tick retry once recovered) or ensure the ping row's failure is retried (the queue retries up to `MAX_ATTEMPTS`). Simplest: the FollowUpWorker skips enqueuing a ping for a conversation whose owning sender is currently restricted, and re-evaluates next tick — auto-finish still fires on the time threshold regardless (D-14). **Recommendation: skip-and-retry-next-tick; auto-finish is sender-independent.**

## Open Questions

1. **Does "timers do not fire while paused" (D-16) require excluding pause-duration from the silence clock?**
   - What we know: the tick won't act on paused campaigns, so no pings/finishes fire during pause. `last_outbound_at` doesn't advance.
   - What's unclear: wall-clock silence accrued during a long pause still counts on resume — a dialog could auto-finish moments after resume. D-16 says "resume continues," which reads as "don't reset," but a strict reading of "timers do not fire while paused" could mean elapsed-during-pause should be added back.
   - Recommendation: implement the simple version (wall-clock, no pause-compensation) for v1; flag to the user in the plan. Adding pause-duration compensation needs a `paused_at` reference and per-conversation clock adjustment — heavier, likely YAGNI.

2. **Ping text: generate-in-tick (Pattern 4a) vs generate-at-send (4b)?**
   - Recommendation: 4a (generate just before enqueue + double guard). 4b touches the protected send path to add an LLM call it has never made — higher risk. Confirm with planner.

3. **Store `last_outbound_at` as a column vs derive via `MAX(messages.created_at)` per tick?**
   - Recommendation: derive lazily for v1 (correctness, no write-scatter across 3 send paths); optimize later if needed. Confirm.
