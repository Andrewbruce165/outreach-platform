# Phase 19: No Reply Follow-Up and Auto-Finish - Context

**Gathered:** 2026-07-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Contacts we messaged and who haven't replied get a "no reply" state; campaigns gain an Enable Follow Up toggle with a user-defined ping interval and an auto-finish after N hours without reply, configurable in the campaign create/edit form. (ROADMAP.md Phase 19, depends on Phase 18.)

</domain>

<decisions>
## Implementation Decisions

### No-reply state semantics
- **D-01:** `no_reply` becomes a new `Conversation.status` value — extend the CHECK constraint (`active|manual|paused|lead|handoff|finished` + `no_reply`). Visible in inbox filters and analytics via the existing status mechanism.
- **D-02:** A conversation flips to `no_reply` only after the first ping interval elapses without an incoming message — NOT immediately after the opener. Status flip and first ping fire off the same timer expiry.
- **D-03:** Any incoming message from the contact returns the conversation to `active` and cancels all scheduled pings for it.
- **D-04:** Silence timer counts from the **last outgoing message** (opener, AI reply, or previous ping). Each ping restarts the timer for the next one.

### Follow-up scope (who gets pinged)
- **D-05:** Pings cover **all silent dialogs**, both kinds: (a) contact never replied to the opener, and (b) contact replied earlier but went silent mid-dialog. User explicitly chose the wider scope over never-replied-only.
- **D-06:** Only conversations with `status='active'` are eligible for pings (plus `no_reply` itself once flipped — the state the machine puts them into). `lead`, `handoff`, `manual`, `paused`, `finished` are NEVER pinged — those are either in a manager's hands or deliberately stopped.

### Ping content
- **D-07:** Ping text is **AI-generated by the campaign's agent** with full dialog history in context (critical for mid-dialog ghosting where a canned template would be off-topic). Reuses the existing ai_engine/prompt-assembly infrastructure; goes through the campaign's configured LLM provider (Phase 18).
- **D-08:** Max pings before auto-finish is a **configurable field in the campaign form** (default 2, bounds 1–5). Auto-finish also fires on the time threshold — whichever comes first.

### Auto-finish behavior
- **D-09:** On auto-finish: conversation → `status='finished'`, all scheduled pings cancelled, existing `finish_webhook_url` fired (if configured) with a `no_reply` reason marker so consumers can distinguish silence-close from dialog-complete.
- **D-10:** Auto-finish N hours counts from the **last outgoing message** (same anchor as the ping timer — one point of reference).
- **D-11:** Auto-finished contacts are eligible for re-contact **by the existing rules** (`allow_recontact` + `recontact_min_age_days`, Phase 9/migration 026). `finished` dialogs are already "unprotected" there — no changes needed.

### Scheduler & limits
- **D-12:** Both settings are expressed in **hours**: ping interval (default 24, bounds 4–168) and auto-finish threshold (default 72, bounds 24–720). Follow Up toggle defaults to OFF.
- **D-13:** Pings are delivered **through message_queue as follow-up items**: campaign working hours and per-sender rate limits (4/min, 20/h, 150/day) fully apply; the daily new-dialog cap and pacing do NOT block them (existing PACE-07 / Phase 12 semantics). Interval expiring at night → ping goes out next working-hours window.
- **D-14:** Ping must come from the **same sender account** that owns the conversation. If that account is frozen/restricted, the ping waits for it to recover; if auto-finish arrives first, the conversation just closes. No failover to another account.

### Toggle lifecycle on running campaigns
- **D-15:** Enabling the toggle on an already-running campaign applies **retroactively with smoothing**: existing silent dialogs also get pings, and the queue + rate limits naturally spread the wave (no burst). Dialogs already past the auto-finish threshold at enable time are finished immediately, without pings.
- **D-16:** Campaign `paused` **freezes everything**: no pings sent AND auto-finish timers do not fire while paused; resume continues. Campaign `done` → all scheduled pings cancelled permanently.

### Races & edge cases
- **D-17:** An incoming message from the contact **cancels any pending ping** in the queue. Double protection: the listener cancels on receipt AND the queue worker re-checks "has the contact replied since this ping was scheduled?" right before sending. The normal AI answerer handles the reply.

### Claude's Discretion
- Exact mechanism for timer evaluation (dedicated scheduler loop vs. piggyback on existing queue worker tick) — planner/researcher decide based on existing worker architecture.
- Where ping counters / next-ping-due state live (columns on conversations vs. a separate table).
- Exact prompt wording for the AI follow-up generation.
- Webhook payload shape for the `no_reply` reason marker (consistent with existing finish webhook payloads).
- UI placement of the Follow Up block within the campaign create/edit form (fits the existing settings patterns like recontact / max_new_dialogs_per_day).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **message_queue follow-up path**: queue already distinguishes follow-up items from new-dialog items; follow-ups bypass daily cap and pacing but respect rate limits and working windows — pings slot into this path with zero changes to throttling logic
- **ai_engine + LLM provider layer (Phase 18)**: AI ping generation is "one more prompt assembly call" through existing infra
- **finish_webhook_url + webhook_notify service**: auto-finish reuses the existing finish notification path (add reason field)
- **Campaign form settings pattern**: recontact toggle + numeric bounds (`allow_recontact`, `recontact_min_age_days`, `max_new_dialogs_per_day`) — the Follow Up block follows the same API-validated-bounds, no-DB-CHECK pattern
- **Conversation status CHECK**: VARCHAR + CHECK constraint (not SQLEnum) — extending with `no_reply` is a simple idempotent migration

### Established Patterns
- Statuses as VARCHAR + DB CHECK (ALTER-friendly), bounds enforced at API layer (Pydantic), not DB
- Queue snapshots message text at enqueue (memory: queue-snapshots-template-at-enqueue) — since pings are AI-generated, generate text at send time (or just-before-send), NOT at schedule time, or a contact reply between schedule and send produces a stale ping
- Listener (separate container) handles incoming messages — the natural place for D-03/D-17 cancel-on-reply
- Workers poll Postgres with `FOR UPDATE SKIP LOCKED`; no Redis/Celery — the ping scheduler should follow the same DB-poll pattern

### Integration Points
- `app/routers/campaigns.py` — POST/PATCH validation for the three new campaign fields + toggle
- `app/services/listener.py` — incoming message hook: revert `no_reply`→`active`, cancel pending pings
- `app/services/queue.py` — pre-send re-check "contact replied since scheduling" (D-17 second guard)
- `lovable-handoff/openapi.json` — regenerate after API changes (Lovable frontend contract)
- Frontend repo `/root/apps/aimly/aimly-tg-outreach` — campaign form UI for the Follow Up block

</code_context>

<specifics>
## Specific Ideas

- User explicitly widened scope beyond the roadmap's literal "haven't replied": ghosted-mid-dialog contacts are in scope too, which is why AI-generated (not templated) ping text was chosen — a canned template mid-conversation would read as a bot.
- Safety-first defaults: toggle OFF, 24h interval, 2 pings max, 72h auto-finish — conservative "green corridor" style consistent with the project's account-safety philosophy.

</specifics>

<deferred>
## Deferred Ideas

- Pinging `lead`/`handoff` dialogs that went silent — deliberately excluded (manager owns those); could be a future "lead nudge" phase.
- Multi-step sequenced follow-ups with distinct per-step templates (ADVN-01 in REQUIREMENTS.md) — this phase delivers uniform AI pings, not authored sequences.
- Distinct terminal status / analytics breakdown for silence-closed vs dialog-closed conversations — covered minimally by the webhook reason marker; a dedicated status or analytics dimension deferred.
