<objective>
Enforce the per-sender-per-campaign daily new-dialog cap inside the candidate selection of `_process_next_for_sender` (queue.py:273-339). When `(sender_id, campaign_id)` has already opened `>= campaigns.max_new_dialogs_per_day` unique NEW dialogs over a trailing-24h rolling window, exclude that campaign's new-dialog items from the LIMIT 8 candidate set — while follow-up / re-contact items (a recipient_phone that already has a prior `status='sent'` in THIS campaign) stay eligible and are sent.

Purpose: Deliver the roadmap promise — cap cold dialogs to reduce spam-ban risk without ever blocking follow-ups (D-07: NOT in `_check_rate_limits`, which is a per-tick gate that would block the whole tick incl. follow-ups). The empirical per-sender limits stay untouched (D-09).
Output: queue.py filter + a full integration test via test-overlay.
</objective>

    Implementation (recommended CTE shape — preserves LIMIT 8 / SKIP LOCKED on `mq`):

    Extend the SELECT so each candidate row is classified as new-dialog vs follow-up, and exclude new-dialog rows when the per-(sender,campaign) cap is reached. Add to the existing FROM/WHERE:

    1. Select `c.max_new_dialogs_per_day AS c_cap` and `mq.recipient_phone`, `mq.campaign_id` alongside the existing columns.
    2. Add a correlated-subquery boolean `is_followup` for each candidate:
       ```
       EXISTS (
         SELECT 1 FROM message_queue prior
         WHERE prior.campaign_id = mq.campaign_id
           AND prior.recipient_phone = mq.recipient_phone
           AND prior.status = 'sent'
       ) AS is_followup
       ```
       (D-03/D-06: prior sent to this phone in THIS campaign ⇒ follow-up, not a new dialog. No time bound on the prior — a dialog opened any time ago is still "existing".)
    3. Add a correlated-subquery count of new dialogs already opened by this (sender,campaign) in the trailing 24h:
       ```
       (SELECT COUNT(DISTINCT opened.recipient_phone)
          FROM message_queue opened
         WHERE opened.sender_id = mq.sender_id
           AND opened.campaign_id = mq.campaign_id
           AND opened.status = 'sent'
           AND opened.finished_at >= NOW() - INTERVAL '24 hours') AS new_dialogs_24h
       ```
    4. In the WHERE clause add the exclusion predicate so new-dialog candidates are dropped once the cap is hit, while follow-ups always pass:
       ```
       AND (
         /* follow-up to an existing contact — never blocked by the new-dialog cap (D-06/D-08) */
         EXISTS (
           SELECT 1 FROM message_queue prior
           WHERE prior.campaign_id = mq.campaign_id
             AND prior.recipient_phone = mq.recipient_phone
             AND prior.status = 'sent'
         )
         OR
         /* new dialog — only if this (sender,campaign) is still under the cap (D-01/D-02/D-05) */
         (SELECT COUNT(DISTINCT opened.recipient_phone)
            FROM message_queue opened
           WHERE opened.sender_id = mq.sender_id
             AND opened.campaign_id = mq.campaign_id
             AND opened.status = 'sent'
             AND opened.finished_at >= NOW() - INTERVAL '24 hours') < c.max_new_dialogs_per_day
       )
       ```
       Keep the existing `ORDER BY mq.priority DESC, mq.created_at ASC LIMIT 8 FOR UPDATE OF mq SKIP LOCKED`. `FOR UPDATE OF mq` must name only `mq` (not the JOINed `campaigns`) — preserved as-is.

    Note (correctness vs the existing per-item Python loop): the existing Python loop iterates the up-to-8 candidates and picks the first one passing the working-window/stop_date checks. The new-dialog exclusion happens in SQL (WHERE), so excluded new-dialog items simply never appear in the candidate set; follow-ups and under-cap new dialogs flow through the unchanged loop.
