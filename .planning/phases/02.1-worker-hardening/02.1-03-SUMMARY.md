### Task 1 — CR-07: lockdown /api/v1/health

**Файл:** `app/routers/health.py` (полный перепиш — 64 → 47 строк)

### Task 2 — CR-08: ContactCheckWorker race protection

**Файл:** `app/services/contact_check_worker.py` (метод `_tick`, ~50 строк изменений)

**До:** `SELECT ... LIMIT :n` без row-lock'а. При двух container'ах оба worker'а брали одни и те же pending контакты → дублирующий вызов checker'а → лишний rate-limit burn на Telegram, лишний bcrypt CPU.

**После — двойная защита:**

1. **In-transaction row lock**: SELECT обёрнут в `async with db.begin()` и расширен `FOR UPDATE OF c SKIP LOCKED`. Другой worker, выполняющий тот же SELECT параллельно, пропускает lock'нутые rows и берёт следующую партию.

2. **Persistent claim window**: сразу после SELECT'а — `UPDATE contacts SET tg_checked_at = NOW() WHERE id = ANY(:ids)` в той же транзакции. Фильтр SELECT'а:
   ```sql
   AND (c.tg_checked_at IS NULL OR c.tg_checked_at < NOW() - INTERVAL '5 minutes')
   ```
   Это переживает commit транзакции — другой worker на **следующем тике** пропустит recently-claimed rows.

**Stale-claim recovery:** если worker упал между SELECT и `_apply_results`, через 5 минут фильтр снова допустит contact — нет блокировки навечно.

**Почему `tg_checked_at`, а не `tg_status='processing'`?** CHECK constraint миграции 013 разрешает только `'pending' | 'registered' | 'not_registered' | 'error' | 'unchecked'`. Добавление `'processing'` требовало бы новой миграции — избыточный риск; `tg_checked_at`-claim даёт ту же гарантию с меньшим disruption.

**Тесты:** `tests/test_contact_check_worker_skip_locked.py`
- `test_sql_uses_for_update_skip_locked` — статический grep по исходнику `_tick`
- `test_recently_claimed_contacts_skipped` — 2 из 3 контактов с `tg_checked_at = NOW()` → worker берёт только 1
- `test_stale_claim_recovered_after_5_min` — контакт с `tg_checked_at = NOW() - 10 min` подбирается
- `test_claim_update_sets_tg_checked_at` — после tick'а все processed контакты имеют свежий `tg_checked_at`

**Commit:** `be1bf39 fix(02.1-03): FOR UPDATE SKIP LOCKED + tg_checked_at claim in ContactCheckWorker (CR-08)`

### Task 3 — CR-09: _verify_api_key cache + constant-time + clean datetime

**Файл:** `app/utils/auth.py` (~80 строк изменений)

**Три sub-issues:**

| # | Issue | Фикс |
|---|-------|------|
| 1 | Timing attack: prefix string-comparison в Python | `hmac.compare_digest(prefix.encode(), candidate.prefix.encode())` — constant-time defence-in-depth поверх SQL prefix-фильтра |
| 2 | CPU bottleneck: bcrypt ~100ms на каждый X-Workspace-Key request → 100 RPS n8n push = 100% CPU на api-контейнере | In-process cache `_TOKEN_CACHE: dict[str, tuple[AuthCtx, float]]` с 5-min TTL, bounded 1024 entries, eviction = ~10% oldest. Helpers `_cache_get`/`_cache_put` |
| 3 | Anti-pattern: `last_used_at = func.now()` (SQL expression в Python attribute) | `last_used_at = datetime.now(timezone.utc)` |

**Архитектура cache:**
```python
_TOKEN_CACHE: dict[str, tuple[AuthCtx, float]] = {}
_TOKEN_CACHE_TTL_SECONDS = 300.0  # 5 минут
_TOKEN_CACHE_MAX_SIZE = 1024
```

**Известные ограничения (документированы в коде):**
- Cache **per-process** — не shared между containers; второй container прогреет свой cache на первых запросах (OK).
- Revoke **не инвалидирует мгновенно** — старый ctx живёт до 5 минут после revoke. Acceptable в v1 (revoke редкий). v2 — Redis pubsub или DB poll.
- Cache `_TOKEN_CACHE_MAX_SIZE = 1024` достаточно для v1 (≤1024 уникальных n8n integrations одновременно активных).

**Тесты:** `tests/test_auth_api_key_cache.py`
- `test_first_call_does_bcrypt` — первый call → bcrypt.checkpw вызван
- `test_second_call_hits_cache` — второй call с тем же raw_token → bcrypt НЕ вызван (cache hit)
- `test_cache_ttl_expired_falls_back_to_bcrypt` — после ручного expire entry → bcrypt вызван снова
- `test_invalid_token_not_cached` — невалидный токен → 401 → НЕ попадает в cache
- `test_last_used_at_is_python_datetime` — после `_verify_api_key` candidate.last_used_at — `datetime`, не `func.now()`
- `test_source_uses_hmac_compare_digest` — статический guard на наличие `hmac.compare_digest` в исходнике
- `test_module_exposes_token_cache` — smoke: `_TOKEN_CACHE` экспонирован, TTL >= 60s

**Commit:** `b892084 fix(02.1-03): _verify_api_key — LRU cache + hmac + clean datetime (CR-09)`
