<objective>
Close Gap A from the 14-04 live-smoke failure: a freshly-throttled checker (FloodWait or an anomalous all-/near-all-empty resolve rate) must NOT finalize its empty resolves as `not_registered`/`high`/`clean`. The 14-04 smoke proved the decoupled control-probe (≥2-miss accumulation in `_probe_cycle`) flags a checker only AFTER an entire poisoned batch has already been finalized — control-probe wrote ZERO `sender_restriction_events` and suspect-rollback never fired while both "healthy" checkers logged `checked=20..30 reg=0 flood=True`.

This plan adds an INLINE flood/throttle degradation trigger at the resolve tick itself, reusing the already-built D-07 suspect-rollback path (`_apply_results` `probe_state='suspect'`) and the D-06 inline degrade (`_flag_checker_degraded`), so a flood batch rolls its negatives back to `pending`, never carries high-confidence, and the checker leaves rotation immediately — without waiting for the separate probe.

Purpose: This is the locked correctness contract from `.planning/notes/checker-false-negatives.md` §"Часть 2". It is the unambiguous code fix that MUST land before any re-activation can be reconsidered.
Output: `contact_check_worker.py` with inline flood-aware finalization + RED-first tests in the existing 14-01 scaffold style proving it.
</objective>
