Current selection (the hole):
```sql
JOIN LATERAL (
    SELECT id, slug, session_string, proxy
    FROM senders
    WHERE workspace_id = c.workspace_id
      AND role = 'checker'
      AND auth_status = 'ok'
    LIMIT 1
) s ON TRUE
WHERE c.tg_status = 'pending'
  AND (c.phone IS NOT NULL OR c.username IS NOT NULL)
  AND (c.tg_checked_at IS NULL OR c.tg_checked_at < NOW() - INTERVAL '5 minutes')
ORDER BY c.created_at ASC
LIMIT :n
FOR UPDATE OF c SKIP LOCKED
```

<threat_model>
ASVS L1. Threats mitigated by THIS plan:
- **Degraded/malicious checker finalizing false not_registered (data-integrity, core bug):** RESV-05 adds `AND restriction_status='none' AND lifecycle_status <> 'paused'` to the JOIN LATERAL. This is the gate that makes a `spam_limited` flag (written by Plan 03's probe) actually stop the worker — closing the exact hole that let `sender-8428118140` keep lying. Mitigation = the two ANDs.
- **Self-inflicted shadow-ban DoS (account safety):** RESV-02 caps per-batch resolves at `burst_cap` (≤30, under the ~45-50 onset) and enforces a per-checker `daily_cap` counted from a DURABLE source (contacts_cache writes today) so a container restart cannot reset the counter and let a checker over-resolve. Cooldown via `restricted_until` is already durable. Mitigation = burst LIMIT + durable daily count + cooldown gate.
- **Confidence-spoofing (defence-in-depth):** by excluding paused/restricted checkers at selection, no suspect checker reaches `_apply_results` to write a `high`-confidence finalization. The finalization-trust rule (Plan 03) thus only ever runs for eligible checkers.
No new endpoints/secrets/PII. All changes are SQL predicates + a count query.
</threat_model>
