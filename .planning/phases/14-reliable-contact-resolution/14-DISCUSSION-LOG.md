## Модель резолва (главная развилка)

| Option | Description | Selected |
|--------|-------------|----------|
| Управляемый пул | Отдельный воркер резолвит батчами через пул чекеров (probe+кап+ротация); предварительное знание «сколько живых» | ✓ |
| Ленивый резолв при отправке | Сендер резолвит номер в момент отправки; нет предзнания, сложнее планировать кампанию | |
| Гибрид | Пул для предчека + ленивый fallback на момент отправки | |

**User's choice:** Управляемый пул
**Notes:** RESV-02/03 уже описаны под эту модель.

### Метод резолва внутри пула

| Option | Description | Selected |
|--------|-------------|----------|
| resolvePhone только | Чистый resolvePhone без побочки; importContacts засоряет адресную книгу | |
| resolvePhone + importContacts fallback | Дублирует поведение здоровых сендеров, макс. покрытие, но больше нагрузки и засоряет контакты | ✓ |

**User's choice:** resolvePhone + importContacts fallback
**Notes:** Зафиксирована заметка: адресную книгу чекеров надо периодически чистить.

## Откуда брать чекеров

| Option | Description | Selected |
|--------|-------------|----------|
| Выделенные чекеры | Отдельные role='checker' аккаунты, не в отправке; throttle бьёт только по резолву | ✓ |
| Временно задействовать сендеров | Часть из 13 сендеров резолвят; быстрый старт, но риск для отправки | |
| Гибрид: выделенные + senders как резерв | Выделенные основные, сендеры — только при большом беклоге в малом темпе | |

**User's choice:** Выделенные чекеры

### Сколько аккаунтов в пуле

| Option | Description | Selected |
|--------|-------------|----------|
| 2–3 аккаунта | Достаточно для ротации и отдыха | ✓ |
| 1 аккаунт пока | Ротация невозможна; пул проектируется но работает с N=1 | |
| 4+ аккаунтов | Макс. пропускная способность; требует онбординга нескольких новых | |

**User's choice:** 2–3 аккаунта
**Notes:** Сейчас активных чекеров 0 → нужно онбордить перед запуском.

## Чувствительность health-probe

| Option | Description | Selected |
|--------|-------------|----------|
| ≥2 промаха подряд | Срабатывает только при 2+ ложных подряд; отсекает шум | ✓ |
| 1 промах = стоп | Любой промах → cooldown; частые ложные тревоги → простои | |
| Порог hit-rate пробы | Проба K контролей/батч; ниже порога (<80%) → затроттлен; гибче но сложнее | |

**User's choice:** ≥2 промаха подряд
**Notes:** Калибровка: 48/49 live, первый ложный на позиции 49 — единичный промах бывает шумом.

### Судьба suspect-пачки

| Option | Description | Selected |
|--------|-------------|----------|
| Всю пачку → pending | not_registered текущей пачки откатываются в pending; registered остаются | ✓ |
| Пометить suspect, не откатывать | Низкий confidence, перечек позже фоном | |
| Откатить всё с последнего чистого probe | Консервативно: откат с момента последней успешной пробы | |

**User's choice:** Всю пачку → pending
**Notes:** Батч ≤30 + проба каждый батч ⇒ «текущая пачка» ≈ окно с последней чистой пробы (опции сходятся).

## Перечек + политика confidence

| Option | Description | Selected |
|--------|-------------|----------|
| Обычная очередь, мобильные первыми | Всё pending тем же пулом непрерывно; приоритет мобильным (~50% живых); без backfill-кода | ✓ |
| Разовый backfill-скрипт | Отдельный одноразовый прогон для 2809 контаминированных; дублирует логику | |
| FIFO без приоритета | Резолвить всё по порядку; живые лиды находятся медленнее | |

**User's choice:** Обычная очередь, мобильные первыми

### Трактовка not_registered по confidence

| Option | Description | Selected |
|--------|-------------|----------|
| Только healthy-checker = финал | not_registered финален только от чекера с чистой пробой; низкий confidence → перечек | ✓ |
| Любой not_registered = финал | Как сейчас; возвращает риск ложных «нет» | |
| confidence храним, потребление позже | В фазе только пишем confidence/source, реакцию кампании откладываем | |

**User's choice:** Только healthy-checker = финал
