<threat_model>
ASVS L1. Threats mitigated by THIS plan (the security core of the phase):
- **Degraded checker finalizing false not_registered (data-integrity, the core bug):** the control-probe (≥2 consecutive misses, D-05) detects a silently throttled checker that produces no errors, only false negatives. On detect, the suspect batch's `not_registered` is written as `pending` (re-checkable), NEVER `not_registered` (D-07). Mitigation = probe + suspect rollback + the `pending`-not-`final` write.
- **Confidence-spoofing (cannot trust a suspect checker):** finalization writes `tg_confidence='high'`/`tg_probe_state='clean'` ONLY when the checker's probe is clean; a degraded checker's negatives never get a confidence stamp and never finalize. Mitigation = the confidence/probe_state write keyed on probe result.
- **Probe-bypass attack on the safety mechanism:** the probe MUST force a live `ResolvePhoneRequest` (skip `_lookup_cache`), or a cached hit makes a throttled checker pass the probe (Pitfall 1) — defeating the entire detector. Mitigation = dedicated live-only probe path.
- **Address-book PII leakage / profile drift (account safety, importContacts):** `ImportContactsRequest` writes the imported number's PII into the checker's address book and shifts its behavioural profile (the very thing that got the original checker shadow-banned). Mitigation = `DeleteContactsRequest` cleanup per import + gate behind the burst-cap; periodic `ResetSavedContactsRequest` janitor noted as a recurring task.
- **Session/PII in logs:** the probe/fallback path must never log decrypted session strings or full imported-contact PII (CLAUDE.md security rule).
Marking via `restriction_status` (not `auth_status`) per Pitfall 2 — `auth_status` stays 'ok'.
</threat_model>
