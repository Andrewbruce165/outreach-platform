# Phase 22: Account-level new-chat limit grades - Context

**Gathered:** 2026-07-07, **rewritten:** 2026-07-08 (user redefined scope via `/gsd:add-phase` — supersedes the original warmup-pool-only design kept below as `[SUPERSEDED]`), **discuss-phase completed:** 2026-07-08

<domain>
## Phase Boundary

Сегодня «сколько новых чатов в сутки может открыть sender» решается на уровне **кампании** (`campaigns.max_new_dialogs_per_day`, Phase 12) — но один и тот же sender открывает новые чаты не только в кампаниях, но и в warmup-паринге (Phase 15), поэтому кампанийный кап не видит суммарную нагрузку на аккаунт и его легко превысить.

**Новая модель:**
1. Лимит «новых чатов в сутки» переезжает с кампании на **аккаунт (sender)** — единый глобальный счётчик на sender, а не на пару (sender, campaign), и не привязан к конкретной кампании (см. D-13: sender-wide dedup).
2. Грейд растёт автоматически по **настраиваемой на уровне workspace лестнице** из 3 фиксированных уровней (лимит/сутки + шаг в днях на каждом), дефолт = 5/9/13 при шаге 30 дней. Модель хранения — `current_level` + `level_updated_at` (см. D-14/D-15), НЕ статичные бакеты по `senders.created_at`.
3. Грейд/лимит — **единый источник** для любого источника новых чатов: и рассылка (campaign cold-open), и прогрев (warmup pairing) тратят один и тот же суточный бюджет аккаунта (с приоритетом рассылки, см. D-09).
4. Пользователь может **вручную переопределить** текущий грейд конкретного аккаунта из карточки в UI (D-15) — это не разовый бесследный оверрайд, а полноценный сброс таймера авто-прогрессии.
5. Отдельно и **независимо** от пунктов 1–4: убрать лимит «количество исходящих сообщений в сутки» (сейчас `senders.rate_per_day`, default 150, гейт в `queue.py::_check_rate_limits` строка ~682) из бэкенда и из UI — по словам пользователя, это ограничение ни на что не влияет.

**Вне scope / не трогаем:**
- `rate_per_min` (4/мин) и `rate_per_hour` (20/час) — убираем только `rate_per_day` (150/день).
- Базовый 20–55с per-send интервал, fatigue-фактор, длинные паузы, retry/FloodWait-логику (CLAUDE.md guard).
- Follow-up'ы и ответы — как и сейчас, не тратят и не гейтятся лимитом новых чатов (только НОВЫЕ диалоги).
- Произвольное число уровней лестницы (add/remove) — фиксировано 3 уровня, редактируются только лимит+шаг каждого (D-16).

## Зафиксированные решения (пользователем, при создании фазы)

- **D-01:** Лимит новых чатов в сутки — на уровне **аккаунта**, не кампании. Заменяет `campaigns.max_new_dialogs_per_day` (Phase 12) как основной гейт для новых диалогов.
- **D-02 (пересмотрено discuss-phase, см. D-14/D-15):** Грейд растёт автоматически, без ручного вмешательства администратора backend — но пользователь ДОЛЖЕН иметь возможность вручную переопределить грейд из UI (новое требование, см. ниже). Итоговый механизм — D-14/D-15.
- **D-03:** Лимит **глобальный** — общий и для рассылки, и для прогрева (Phase 15 warmup pairing тоже создаёт «новые чаты» и должен тратить тот же бюджет).
- **D-04:** Убрать лимит «исходящих сообщений в сутки» (`senders.rate_per_day` / 150 по умолчанию) целиком — из backend-гейта (`queue.py::_check_rate_limits`) и из UI (там, где показывается/редактируется этот лимит для sender'а).

## Решения, зафиксированные в discuss-phase (2026-07-08)

### Pacing внутри рабочего окна
- **D-05:** Если у sender'а ОДНА активная кампания — pacing (формула `expected_now` из Phase 13, `queue.py:385-440`) продолжает брать рабочее окно (timezone/work_hour_start/end/work_days_mask) **ЭТОЙ кампании**. Меняется только числитель лимита: вместо `c.max_new_dialogs_per_day` (кампанийный кап) — аккаунтный грейд-бюджет sender'а. Минимальное изменение существующего кода Phase 13.

### Распределение бюджета между несколькими активными кампаниями
- **D-06:** Если у sender'а 2+ активные кампании одновременно — общий аккаунтный бюджет делится **FIFO по очереди**: побеждает кампания, чей элемент в очереди стоит первым по существующему `ORDER BY priority DESC, created_at ASC` (`_process_next_for_sender`). Никакой новой логики распределения/приоритета кампаний не вводится — счётчик расхода бюджета переезжает с уровня `(sender_id, campaign_id)` на уровень `sender_id`.

### Судьба `campaigns.max_new_dialogs_per_day`
- **D-07:** Колонка **дропается полностью**. Аккаунтный грейд — единственный источник правды для лимита новых диалогов. Требует: миграции удаления колонки (или depreciation), чистки API/схем (`CampaignCreate`/`CampaignUpdate`/`CampaignResponse`), чистки UI-поля в форме кампании, чистки SQL в `queue.py` (`c.max_new_dialogs_per_day` → аккаунтный бюджет).

### Определение «нового чата» для аккаунтного бюджета (sender-wide dedup)
- **D-13:** «Новый диалог» на аккаунтном уровне определяется **sender-wide**, а не per-campaign, как сейчас (Phase 12 D-03). Если sender уже отправлял `status='sent'` этому `recipient_phone` В ЛЮБОЙ своей кампании — это НЕ новый чат (follow-up-подобно), бюджет не тратится, даже если это первое сообщение в ТЕКУЩЕЙ кампании. Обоснование: для Telegram anti-spam это уже знакомый peer независимо от того, через какую внутреннюю кампанию идёт переписка. Меняет предикат `EXISTS (... AND prior.campaign_id = mq.campaign_id ...)` → убрать привязку к `campaign_id`, оставить `prior.sender_id = mq.sender_id AND prior.recipient_phone = mq.recipient_phone AND prior.status = 'sent'`.

### Warmup: known-pair-free + приоритет рассылки
- **D-08:** Warmup сейчас full-mesh (`_create_new_sessions`, `warmup.py:541-629`) — одна и та же пара аккаунтов переписывается снова и снова после каждой завершённой сессии. Бюджет «новых чатов» тратит **только НОВАЯ пара** (аккаунты, которые ещё никогда не переписывались через warmup). Нужен реестр `sender_first_contacts` (или аналогичная таблица) — первая сессия между двумя конкретными sender'ами тратит бюджет инициатора, повторные сессии той же пары — бесплатны. Со временем full-mesh исчерпывает все возможные пары в пуле, и новых трат почти не остаётся (несёт риск: см. Claude's Discretion — кто «инициатор» новой пары для списания бюджета).
- **D-09:** Рассылка **в приоритете** на общий бюджет: warmup тратит только остаток аккаунтного бюджета после резерва под pending cold openers кампаний sender'а на сегодня (аналогично `[SUPERSEDED]` D-11 ниже — резерв = бюджет − потрачено_за_окно − pending). Рассылка никогда не недополучит бюджет из-за прогрева.

### Источник возраста аккаунта для грейда (bulk-import)
- **D-10:** Bulk-импортированные (Phase 21) аккаунты, даже реально старые/прогретые, **стартуют с грейда 1** (`level_updated_at` = момент создания строки sender, как и `created_at` сегодня) — осознанно принятый риск, без ручного override при импорте. Если аккаунт реально старый — пользователь может **вручную поднять грейд** через UI (D-15), это и есть предусмотренный manual escape hatch.

### Конфигурируемая лестница грейдов (новое расширение scope пользователем)
- **D-16:** Лестница грейдов настраивается на уровне **workspace** (аналогично `warmup_settings`, Phase 15 D-10), а не глобальной код-константой. **Фиксированные 3 уровня** (не произвольное количество) — пользователь редактирует для каждого: лимит новых чатов/сутки + шаг в днях до следующего уровня. Дефолт = уровень 1: 5/сутки, шаг 30д; уровень 2: 9/сутки, шаг 30д; уровень 3: 13/сутки (потолок, шаг не имеет смысла — см. D-17). Нужна новая таблица/строка настроек (по паттерну `warmup_settings`) + GET/PUT эндпоинты + регенерация openapi.json.
- **D-17:** На верхнем (3-м) уровне лестницы грейд **остаётся навсегда** — нет дальнейшего перехода, `level_updated_at` на этом уровне не имеет операционного значения (только историческая метка последнего перехода/оверрайда).

### Модель хранения и авто-прогрессии грейда
- **D-14:** Схема: `senders.current_level` (int, 1..3, default 1) + `senders.level_updated_at` (timestamptz, default = `created_at` для новых/существующих строк при бэкфилле). Авто-прогрессия: когда `NOW() - level_updated_at >= шаг_дней(current_level)` (шаг берётся из workspace-настройки лестницы, D-16) — `current_level += 1`, `level_updated_at = NOW()`. На уровне 3 переход не происходит никогда (D-17).
- **D-15:** Ручной оверрайд грейда из карточки аккаунта в UI пишет `current_level = <выбранное>`, `level_updated_at = NOW()` — **той же операцией**, что и авто-переход. Не отдельный "замороженный" флаг: после ручного повышения таймер до следующего авто-повышения просто перезапускается по тем же правилам лестницы. Явного бессрочного "заморозить и никогда не трогать" режима нет — если нужно держать аккаунт на конкретном уровне вечно, это означает грейд 3 (D-17) либо повторные ручные оверрайды.

### UI-контракт (новое расширение scope пользователем)
- **D-11 (UI):** Страница добавления/списка аккаунтов (senders) получает:
  1. Настройку лестницы грейдов на уровне workspace (D-16) — 3 строки «лимит/сутки» + «дней до следующего уровня» с зелёным коридором по аналогии с существующими rate-limit warning'ами.
  2. На карточке каждого аккаунта — отображение текущего грейда/уровня + (желательно) прогресс до следующего уровня и текущий остаток дневного бюджета.
  3. На карточке аккаунта — контрол ручного изменения грейда (D-15).
- **D-12:** Обновить `lovable-handoff/openapi.json` + типы после реализации API (GET/PUT настроек лестницы workspace, PATCH грейда sender'а, расширенный `SenderResponse` с `current_level`/`level_updated_at`/остатком бюджета).

### Claude's Discretion
- Точный механизм периодической проверки авто-прогрессии (фоновый тик наподобие `QueueWorker`/`WarmupWorker` vs ленивый пересчёт при чтении/использовании sender'а) — не критично для пользователя, лишь бы грейд был корректен к моменту гейта в очереди.
- Схема таблицы `sender_first_contacts` (структура пары, индексы, идемпотентный бэкфилл из существующих `warmup_sessions`/`warmup_messages`, чтобы уже состоявшиеся пары не посчитались новыми задним числом) — реализация D-08.
- Кто именно списывается как «инициатор» новой warmup-пары для целей бюджета (например, менее прогретый vs более прогретый аккаунт, или тот, кто физически шлёт первое сообщение в новой сессии) — реализация D-08, ссылка на `[SUPERSEDED]` D-12 (выбор инициатора: пишет первым более старый/прогретый аккаунт).
- Точный SQL-shape sender-wide дедупа (D-13) и account-level pacing/cap предикатов — сохранить `LIMIT 8` / `FOR UPDATE OF mq SKIP LOCKED` семантику `_process_next_for_sender`.
- Формулировка предупреждений/зелёного коридора для настройки лестницы в UI (по тону существующих D-14-паттернов из senders.py/campaigns.py).
- Где хранить настройку лестницы (новая таблица `sender_grade_settings` vs добавление колонок в существующую `warmup_settings`) — по усмотрению планировщика, слот под workspace-scoped настройки уже есть как паттерн.

## Specific Ideas

- Пользователь явно хочет видеть грейд аккаунта прямо на карточке в UI и иметь возможность его вручную поднять/опустить — это НЕ отменяет автоматику, а работает как ещё один триггер того же перехода (сброс таймера).
- «Зелёный коридор» дефолт 5/9/13 при шаге 30 дней — это сам дефолт лестницы, а не жёстко закодированное значение; workspace может настроить иначе.
- Обоснование sender-wide дедупа (D-13): с точки зрения Telegram anti-spam не важно, через какую внутреннюю кампанию идёт переписка — если peer уже знаком аккаунту, это не новый контакт.

### Базовые принципы
- **D-01:** Гейтим только аккаунты в warmup-пуле; остальные работают как сейчас.
- **D-02:** Бюджет = «новых чатов в сутки» (скользящие 24 ч, как в существующем кап Phase 12 — без взрывов в полночь).
- **D-03:** Рассылка всегда в приоритете: warmup тратит только то, что рассылке сегодня не нужно.
- **D-04:** Лестница: недели 1–3 → 3/день, неделя 4 → 4, неделя 5 → 6, неделя 6 → 8, после 42 дней — кап 8 навсегда. Всё редактируется.

### 1. Схема данных — миграция 053
- **D-05:** `warmup_settings` (существующая таблица, паттерн как у topics): добавляем `levels` JSONB (массив `{days, new_chats_per_day}`), `graduated_cap` INT (дефолт 8), `max_messages_per_day` INT (дефолт 60 — вместо старой лестницы сообщений). NULL/пусто = код-дефолты, поведение без настроек не меняется.
- **D-06:** Новая таблица `sender_first_contacts` (`sender_id`, `peer_phone`, `first_contact_at`) с PK по паре — единственный источник правды «этому peer'у уже писали первым». Бэкфилл в той же миграции из `conversations` + `warmup_messages` (идемпотентно, `ON CONFLICT DO NOTHING`), чтобы существующие диалоги не посчитались новыми.

### 2. Queue worker — гейт рассылки
- **D-07:** В SQL-выборке `_process_next_for_sender` (ветка «new dialog», queue.py:490) добавляется третье условие: если sender активен в warmup-пуле — `COUNT(sender_first_contacts за 24ч) < бюджет_уровня`. Follow-up'ы и ответы не трогаем (как и сейчас). Исчерпан бюджет → opener просто ждёт, не сгорает.
- **D-08:** Бюджет уровня считается в Python по `enrolled_at` и передаётся биндом (по образцу `expected_now` из Phase 13). После успешной отправки cold opener'а — insert в реестр.

### 3. Warmup worker — три изменения
- **D-09:** Убираем лестницу сообщений (LEVEL_CONFIG 5→120/день) → один настраиваемый `max_messages_per_day`. Pacing (≥5 мин между сообщениями, 5 мин–2 ч в диалоге) остаётся.
- **D-10:** Создание новой пары тратит бюджет инициатора. Пара «знакомых» аккаунтов (уже есть в реестре) — бесплатна, как сейчас. Новая пара создаётся только если у инициатора после резерва остаётся ≥1 слот.
- **D-11:** Приоритет рассылки = резерв: остаток = бюджет − потрачено_за_24ч − pending cold openers сендера в очереди на сегодня. Warmup берёт слот только из положительного остатка — рассылка никогда не недополучит.
- **D-12:** Бонус к безопасности — выбор инициатора: первым в новой паре пишет более старый/прогретый аккаунт. Новичок в пуле только получает входящие и отвечает (ответы бюджет не тратят) — его лимит 3/день целиком остаётся рассылке, а входящие чаты для Telegram выглядят максимально естественно.

### 4. API
- **D-13:** `GET/PUT /warmup/settings` — уровни (массив), `graduated_cap`, `max_messages_per_day`; валидация: дни > 0, лимиты 1–50, предупреждение зелёного коридора отдаёт бэкенд (поле `recommended` в ответе).
