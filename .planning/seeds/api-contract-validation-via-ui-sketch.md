## Идея

Перед имплементацией Phase 4 (Campaigns) собрать тонкий UI-sketch ключевого флоу (создание кампании: агент + папка + аккаунты + расписание + сигналы + webhook) и проверить что планируемый API его полностью покрывает.

## Зачем

Текущий план — бэкенд целиком, потом ТЗ для Lovable. Риск: контракт получается неудобным для фронта (не хватает денормализованных полей, нужны endpoints которых не планировали, неудобная пагинация и т.п.) — обнаруживается уже на интеграции, когда переделывать дорого.

Phase 4 — самая сложная связка по UX (множество объектов в одной форме), поэтому именно там цена ошибки контракта максимальна. Phase 3 (Agents) — простой CRUD, sketch не нужен. Phase 5 (Inbox & Analytics) — sketch уже поздно, поскольку зависит от формы данных кампании.

## Как применить

1. После завершения Phase 3, перед `/gsd-plan-phase 4` — запустить `/gsd-sketch` на флоу «создание кампании»
2. По результату sketch'а — скорректировать requirements/endpoints в Phase 4 до планирования
3. Опционально повторить для inbox-флоу перед Phase 5

## Альтернатива (если идея не сработает)

Если sketch не вскроет ничего полезного на Phase 4 — отказаться от практики, продолжать чистый backend-first подход до самого ТЗ.
