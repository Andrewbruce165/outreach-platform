### Root-cause confirmation against LIVE code (2026-07-08, fixing phase)

Re-read the actual files (not just prior evidence). Confirmed EXACT mechanism:
- Frontend `accounts.tsx:1226-1227` (saveProfileMut): `first_name: firstName.trim() || null`, `last_name: lastName.trim() || null`. A cleared last_name → JSON `last_name: null`.
- Backend `senders.py:1119-1123`: builds `UpdateProfileRequest(first_name=..., last_name=..., about=...)` passing request values through directly. `last_name=None` → Telethon OMITS the field (flags.1 unset) → `account.updateProfile` leaves it UNCHANGED (NOT cleared). This is correct Telegram/TL semantics: omitted flagged field = unchanged; explicit `""` = clear.
- Backend cache write `senders.py:1129-1135`: `if request.first_name is not None:` — since the frontend ALSO sends the (unchanged) first_name="Polina", this branch RUNS, composes `"Polina"` (last_name None→falsy→no suffix) and writes `sender.name="Polina"`. So the DB cache is wrongly emptied of the last name even though Telegram still has "Cdxpeo". Exactly matches the live repro (UI shows no last name; refresh brings it back).
- Post-write verify `_verify_profile_applied` (telegram.py:1247-1280): gated `if req_first is not None or req_last is not None`; with `req_last=None` the last_name diff is SKIPPED → no ProfileChangeRejectedError → falls through to success. This is why report #1's verification did not catch report #2.
- KEY INSIGHT: the backend already passes `""` straight through to Telethon AND `_verify_profile_applied` already handles `""` correctly (`"" is not None` → diff runs, compares live value against `_norm("")=""`). So the fix is primarily FRONTEND: send `""` not `null` for an explicitly-cleared field. Backend needs only a first_name-empty guard (Telegram rejects empty first_name with FIRSTNAME_INVALID — first_name cannot be cleared).

fix_plan:
1. Frontend accounts.tsx: `|| null` → `|| ""` for first_name/last_name so a cleared field sends explicit `""`. Add client-side guard: empty first_name → toast + abort (Telegram requires a non-empty first name).
2. Backend senders.py: add a pre-Telegram guard — `request.first_name` explicitly `""`/blank → 400 FIRST_NAME_REQUIRED (clear message, no RPC round-trip / fresh-account throttle risk).
3. Backend: no change needed to UpdateProfileRequest build or `_verify_profile_applied` — both already handle `""` correctly. Verified by reading.
4. Tests: clear-last_name success (verify diffs "" and passes); clear-last_name silently rejected → ProfileChangeRejectedError (no false-empty cache); clear-first_name → 400 FIRST_NAME_REQUIRED.

## Resolution

root_cause: TWO DISTINCT confirmed root causes under the same user-facing symptom ("profile edit doesn't apply to Telegram"):
(1) [FIXED, deployed, awaiting final re-confirmation] Telegram's server-side anti-abuse rate limit on profile-name/bio changes silently no-ops account.UpdateProfileRequest for freshly-created accounts — accepts the RPC without raising FloodWaitError yet does not apply the value. No post-write verification previously existed. Blast radius confirmed larger than initially scoped: bulk resync (2026-07-08) found ~30+ of 63 sender accounts carry garbled real Telegram last names because renaming attempts on freshly-created accounts were silently swallowed for a long time. Retroactive data remediation (bulk-rename on Telegram) is explicitly DEFERRED / out of scope for this debug session.
(2) [FIXED, deployed, awaiting final re-confirmation] Frontend sends cleared first_name/last_name fields as `null` (`firstName.trim() || null`); Telethon treats `None` as "leave field unchanged" rather than "clear it" (unlike `about`/bio which already correctly sends `""` to clear). So clearing a name field is a silent no-op on Telegram, while the app wrongly writes the emptied value into the local DB cache and reports success. The report #1 post-write verification does not catch this because it does not diff fields that were sent as None (nothing to compare against an "attempted change").
fix: (1) Post-write verification implemented — TelegramService.update_profile re-reads live profile via get_me/GetFullUser after UpdateProfileRequest, diffs vs requested values, raises ProfileChangeRejectedError on mismatch (409 PROFILE_CHANGE_REJECTED, RU retry message, no cache write on rejection).
