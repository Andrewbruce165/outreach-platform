## Symptoms

- **Expected:** контакты из CSV (419 строк, телефоны вида +77199704874, +79078…) импортируются в папку как валидные.
- **Actual:** Imported=0, Duplicates=0, Invalid=419, Total=419. Все строки невалидны.
- **Errors:** UI ошибок не показал — мастер дошёл до "Done" с зелёной галкой.
- **Timeline:** воспроизводится стабильно сегодня (2026-06-26). В логах несколько попыток подряд (514, 514, 419, 419 — все invalid).
- **Reproduction:** Import contacts → Upload CSV → Map columns → Import → шаг Done показывает all-invalid.

## Current Focus

- **hypothesis (ROOT CAUSE, mechanism confirmed):** Парсер CSV (`parse_preview`/`apply_import`) НЕ детектит структуру файла корректно, а `normalize_to_e164` слишком слабый (regex `+` + 7–15 цифр) — он молча выбрасывает ВСЕ не-цифры из строки. Для рабочего файла это дало мусорные «валидные» номера (см. Evidence — `+771997048474` 13 цифр, `+11210217907847` 14 цифр в БД). Для провального файла та же логика дала длину вне 7–15 → каждая строка `invalid_phone` → invalid=419. Дополнительно: при no-header списке телефонов первая строка трактуется как header и первый контакт молча теряется.
- **test:** Нужен СВЕЖИЙ blob провального импорта (старые удалены при /import + истёк 30-мин TTL). Без байтов нельзя точно классифицировать invalid_phone vs no_phone_no_username для конкретного файла.
- **expecting:** Подтвердить что провальные строки → `invalid_phone` (нормализатор), а не `no_phone_no_username` (маппинг).
- **next_action:** ROOT CAUSE найден на уровне механизма. Запросить у пользователя свежий импорт ИЛИ исходный CSV; параллельно — surface предлагаемый фикс (усилить normalize_to_e164 + не терять первую строку no-header + логировать mapping/reasons).

  - В 08:10 ОДИН импорт прошёл: `total=420 imported=7 dup=413 invalid=0` (тоже cols=1). Затем 08:11 повтор → `dup=420 invalid=0`.
  - ⇒ Разделитель сам по себе не виноват (рабочий файл тоже cols=1). Разница — в том, на какое поле замаплена единственная колонка ИЛИ в самом файле.
  - workspace=bb96789d-ca84-4880-9568-90867aae6acd, folder=485593f5-81ac-44ec-bd91-af305c7d55ed.

- timestamp: 2026-06-26 — ДАМП БД (folder=485593f5…, рабочий импорт 08:10 imported=7):
  - Импортированные `contacts.phone`: `+771997048474` (13 цифр), `+170113593052`, `+5031136145`, `+11210217907847` (14 цифр), `+79161020432`, `+56013780110`, `+771775702696`. Длины 11–15.
  - ⇒ Это МУСОР: чистый RU-номер = `+7`+10 = 12 цифр. `+771997048474` — это `+7 (719) 970-48-474`-подобная форматированная строка, из которой `normalize_to_e164` выбросил `( ) - пробелы` → склеил все цифры. `+11210217907847` точно воспроизводится из строки вида `+1,121021,7907847` (запятые/мусор стрипаются).
  - ⇒ Слабый нормализатор (`^\+\d{7,15}$`) пропускает мусор как «валидный». Это объясняет и imported=7 (мусор прошёл), и invalid=419 (другой файл → длина вне 7–15).
  - 413 dup из 420 — повторные мусорные значения уже были в БД.

- timestamp: 2026-06-26 — РЕПРО механизма (python, локально):
  - `'+7 (719) 970-48-47'` → norm `'+771997048447'` (точно паттерн мусора в БД).
  - `'+1,121021,7907847'` → norm `'+11210217907847'` (точное совпадение со значением в БД).
  - `'7907847; +79161020432'` → склейка → `'+790784779161020432'` (18 цифр) → None → `invalid_phone`. Это и есть механизм all-invalid: многоколоночные/мусорные строки склеиваются в длину >15.
  - Колонка из имён (кириллица, без цифр) → norm None → `invalid_phone`. Тоже даёт all-invalid если фронт замапил не ту колонку.

- timestamp: 2026-06-26 — РЕПРО потери первой строки (no-header):
  - `parse_preview` на списке телефонов без заголовка → `columns=['+7 (719) 970-48-47']` (первый телефон стал header), `looks_like_no_header=True`, `suggested_mapping={}`.
  - `apply_import(mapping={'0':'phone'})` → `data_rows=rows[1:]` → первый контакт МОЛЧА теряется (off-by-one для no-header файлов). Отдельный баг, не причина all-invalid, но реальный.
  - При `suggested_mapping={}` фронт ОБЯЗАН прислать ручной mapping, иначе `apply_import` бросил бы `MAPPING_INVALID`(422) — а его в логах нет ⇒ phone реально замаплен, значит invalid=419 идёт через ветку `invalid_phone`, не `no_phone_no_username`.

- timestamp: 2026-06-26 — диагностический пробел:
  - В `csv_imports` 0 строк — blob'ы удаляются при `/import` и истекают по 30-мин TTL. Свежий провальный blob недоступен.
  - `logger.info` в `/import` (contacts.py:425-429) НЕ логирует ни `mapping`, ни `skipped_invalid_reasons` — поэтому невозможно классифицировать причину постфактум. `ContactImportSummary` тоже не возвращает reasons → пользователь не видит почему invalid.
