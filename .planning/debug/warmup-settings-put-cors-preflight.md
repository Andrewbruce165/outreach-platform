# Debug Session: warmup-settings-put-cors-preflight

## Symptoms

- **Expected behavior:** Saving warmup settings (master toggle + content) via
  `PUT /api/v1/warmup/settings` from the Lovable frontend should succeed so
  warmup can be enabled.
- **Actual behavior:** The PUT never reaches the backend — Chrome reports
  `net::ERR_FAILED` and blocks it because the CORS preflight (OPTIONS) fails.
- **Error messages:**
  - `PUT .../api/v1/warmup/settings net::ERR_FAILED`
  - `Access to fetch ... blocked by CORS policy: Response to preflight request
    doesn't pass access control check: It does not have HTTP ok status.`
- **Timeline:** Surfaced now that the user is using the warmup feature — this
  is the first time the frontend issues a PUT.
- **Reproduction:** Add warmup accounts, change settings / toggle master in the
  warmup UI on `aimly-tg-outreach.lovable.app`.

## Distinction from prior CORS session

NOT the same as `contacts-import-cors-400` (a 500 escaping CORSMiddleware →
"No Access-Control-Allow-Origin header"). This message — "preflight does not
have HTTP ok status" — is Starlette's CORSMiddleware **rejecting the preflight
itself** with a non-2xx because the requested method is not allowed.

## Current Focus

hypothesis: CORSMiddleware `allow_methods` does not include `PUT`, so the
  OPTIONS preflight for `PUT /warmup/settings` is rejected with 400
  "Disallowed CORS method". `PUT /settings` is the ONLY PUT route in the whole
  backend (every other mutation uses PATCH, which IS allowed) — explaining why
  this never surfaced before.
test: live OPTIONS preflight against prod with Access-Control-Request-Method:
  PUT vs PATCH.
expecting: PUT preflight → non-200; PATCH preflight → 200.
next_action: DONE — root cause confirmed. Fix: add "PUT" to allow_methods.

## Evidence

- timestamp: 2026-06-30T10:25Z
  source: app/main.py:94 (CORSMiddleware config)
  finding: `allow_methods=["GET", "HEAD", "POST", "PATCH", "DELETE", "OPTIONS"]`
    — PUT is absent.

- timestamp: 2026-06-30T10:25Z
  source: grep `\.put(` across app/routers/*.py
  finding: The only PUT route in the entire backend is
    `app/routers/warmup.py:551 @router.put("/settings")`. All other mutations
    use PATCH (campaigns, folders, agents, conversations, workspace, senders,
    warmup pool toggle). PATCH is in allow_methods → those all work; PUT is not
    → only warmup/settings breaks.

- timestamp: 2026-06-30T10:27Z
  source: live OPTIONS preflight against https://aimly.agsventurelab.com
  finding: |
    Access-Control-Request-Method: PUT   → HTTP/1.1 400 Bad Request
    Access-Control-Request-Method: PATCH  → HTTP/1.1 200 OK
    Both return `access-control-allow-methods: GET, HEAD, POST, PATCH, DELETE,
    OPTIONS` (no PUT). Confirms the preflight is rejected solely on the method.

## Eliminated

- nginx / network layer: nginx returns the 400 generated by the app (it proxies
  OPTIONS fine — PATCH preflight returns 200 through the same chain).
- Backend 500 / code bug in the endpoint: the PUT handler is never reached; the
  failure is purely at the CORS preflight gate.

## Resolution

root_cause: |
  Starlette CORSMiddleware `allow_methods` list in app/main.py omits "PUT".
  The browser preflights `PUT /api/v1/warmup/settings` with OPTIONS +
  `Access-Control-Request-Method: PUT`; CORSMiddleware sees PUT is not allowed
  and returns `400 Disallowed CORS method`. A non-2xx preflight makes Chrome
  abort the real PUT with net::ERR_FAILED. Because warmup/settings is the only
  PUT endpoint in the API (everything else is PATCH, which is allowed), this is
  the first request to expose the gap.

fix: |
  Add "PUT" to allow_methods in app/main.py CORSMiddleware config. Rebuild api.
  (Frontend already issues PUT and is Lovable-generated from the openapi spec,
  so changing the endpoint verb to PATCH would desync the contract — widening
  the CORS method list is the correct, minimal fix.)

verification: |
  DEPLOYED 2026-06-30 — `docker compose up -d --build api` succeeded, API up and
  serving live traffic. Live OPTIONS preflight with
  Access-Control-Request-Method: PUT now returns HTTP 200 (was 400), and
  access-control-allow-methods now includes PUT
  (GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS). PATCH control still 200.

files_changed:
  - app/main.py (allow_methods += "PUT")
