## ⚠️ Слой 3 (НОВОЕ, НЕ фикшено — на решение): Phase-17 регрессия резолва warmup-пиров

Часть sends падает `+16185468137 не зарегистрирован в Telegram` — это НЕ session_expired, а **регрессия Phase 17**.
Warmup резолвит телефон пира через `resolve_contact`, у которого Phase 17 (D-01) **убрал собственный
`ResolvePhone` сендера**. Теперь warmup достаёт пира только если пара `(sender_id, peer_phone)` уже в
`contacts_cache` (TTL 7 дней) ИЛИ у номера есть captured `@username` / verdict `registered` в `contacts`.
Но warmup-пиры — наши же аккаунты, их нет в `contacts` → нет verdict → tier-3 import пропускается → `is_registered=False`.

Доказательство: успешный `sender-8525079460 → +16018728956` = cache-hit (пара в кэше, fresh);
падающий `sender-8071536685 → +16185468137` = для этого сендера пары в кэше нет (кэш пер-сендерный).
Кэш заполнялся старым `ResolvePhone` до деплоя Phase 17 (06-30 18:31); **новые пары не резолвятся, старые
протухнут ~07-07** → warmup будет деградировать до полной неработоспособности резолва.

**Решение за пользователем** (дизайн-чувствительно, трогает Phase-17 ладдер — по CLAUDE.md сначала обсуждаем):
- Вариант A: для warmup-пиров (свои аккаунты одного workspace) резолвить пира по известному `telegram_id`
  сендера-пира напрямую (у нас есть их id/phone) — не гонять через contacts-ладдер вообще.
- Вариант B: вернуть sender-side `ResolvePhone` ТОЛЬКО для warmup-пути (не для кампаний, где он и давал FN).
- Вариант C: сидировать `contacts_cache` парами свои-аккаунты при добавлении в warmup_pool.

# Исходный диагноз (08:45 UTC)

**Итог:** причина найдена. Два слоя (третий добавлен выше по ходу фикса).

## TL;DR

Warmup встал в **07:03 UTC** из-за **head-of-line blocking** в `_process_due_sessions`
([app/services/warmup.py:274-282](../../../app/services/warmup.py)): воркер берёт 10 самых ранних due-сессий
(`ORDER BY next_message_at LIMIT 10`), а скип неэлиджибл-сессии (`_process_session`, строка 369-375)
**не сдвигает `next_message_at`** — сессия остаётся в голове очереди навсегда. Как только неэлиджибл-сессий
с ранним `next_message_at` накопилось ровно 10, батч стал заполняться только ими каждые 30 секунд,
и здоровые пары перестали обрабатываться вообще.

Триггер: **4 сендера потеряли Telegram-сессию** (`auth_status='session_expired'`), их warmup-пары стали
перманентно неэлиджибл и забили всю выборку.

## Слой 1: аккаунты с session_expired

| slug | phone | примечание |
|---|---|---|
| sender-7867638054 | +16398525147 | **ca-account-1 — единственный рабочий checker!** Последний warmup 07-01 09:04 |
| sender-8503645757 | +12268774914 | последний warmup 07-01 08:10 |
| sender-8218483045 | +79587869196 | не в warmup-парах |
| sender-8539506204 | +79587860771 | не в warmup-парах |

`session_expired` ставится в `telegram.py:307-326` / `listener.py:1352,1414` при AUTH_ERRORS от Telethon
(AuthKeyUnregistered / SessionRevoked / not authorized) — т.е. сессии реально убиты на стороне Telegram
(вылогинены или терминированы). Когда именно — по логам не видно (контейнеры пересобраны ~08:05 UTC,
старые логи потеряны); по last warmup-сообщениям — между 07-01 ~09:00 и 07-02 утром.

**Критичный сайд-эффект:** ca-account-1 был единственным рабочим чекером (изоляционный тест 2026-06-30,
53% на RU-мобильных). С его смертью проверка контактов (Igor base, 116 unchecked) тоже стоит.

## Слой 2: head-of-line blocking (баг воркера)

10 сессий, намертво забивших батч (все due раньше здоровых, всем скип каждые 30с):

- `4ee8974b` — due **2026-06-30 13:10** (пара с paused sender-7979031303) — блокирует слот 2 дня
- `435dd8fe`, `69d78220`, `c8e1f973`, `84128f77`, `619c7c00` — due 06:08–06:31, пары с session_expired
- `f537c3e5`, `6d8089ff`, `a3d68b8d` — due 06:42–06:44, пары с session_expired (c5c469a4 = ca-account-1)
- `48fb201c` — due **07:03** — десятая; с этого момента LIMIT 10 заполняется только неэлиджиблами

Хронология сходится: последнее отправленное warmup-сообщение — 06:59:13 (sender-8071536685),
последний сдвиг сессии — 07:02. Новые 4 сессии, созданные в 08:43 при добавлении sender-8514716383
в пул, здоровы, но никогда не дойдут до обработки — их `next_message_at` (08:44+) позже головы очереди.

Механика бага: `_process_session` при `not is_eligible` делает `return` без `UPDATE next_message_at`
и без паузы сессии. В `warmup_sessions.status` есть только `active`/`completed` — статуса `paused` нет.
