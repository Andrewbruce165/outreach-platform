<objective>
Mirror the Phase 14/17 checker "suspect / rollback" semantics onto the message-send path so a false-negative resolve from a sick sender is never finalized silently.

Today (proved 2026-07-06): at 07:31:01 `sender-7867638054` returned "+79185782285 не зарегистрирован в Telegram", then 12s later caught PEER_FLOOD. The number was alive (a healthy account sent to it at 08:19). On the send path this class of false-negative is NOT handled the way the dedicated checker handles it: the failed row sticks to the sick sender and the sender's resolve verdict can poison `contacts_cache`.

This plan adds two complementary, bounded behaviours:
1. **Reactive rollback** — when a sender is flagged `spam_limited`/`frozen` (the inline PEER_FLOOD / ACCOUNT_FROZEN path in queue.py), claw back that sender's resolve-based failures (NOT_REGISTERED / PRIVACY) from the last N minutes: reroute those `message_queue` rows onto a healthy pool sender (`status='pending'`, `scheduled_at=NOW()`), and purge the `is_registered=false` `contacts_cache` rows the sick sender wrote in the window.
2. **Preventive re-rotation** — a NOT_REGISTERED result on the send path, when the campaign pool has an untried healthy sender, re-rotates onto that sender instead of finalizing a permanent fail on the same account. Bounded by "all eligible senders tried" → then finalize (genuinely unregistered).

Purpose: false-negatives on the send path stop stranding live leads on a throttled account and stop poisoning the resolve cache — the same guarantee Phase 14/17 already gives the dedicated checker.
Output: new `app/services/send_suspect.py` helper, wiring + a NOT_REGISTERED branch in `app/services/queue.py`, and a test file reproducing the acceptance criteria.

**Chosen window:** `SUSPECT_RESOLVE_WINDOW_MINUTES = 15`. Rationale: the send interval is 20–55s, so 15 min covers roughly the last ~15–40 sends — the pre-restriction throttle ramp during which a sliding-into-spam-limit account emits false negatives before PEER_FLOOD actually fires — while being short enough that genuinely old NOT_REGISTERED results (from a healthy period) are not clawed back. This is NOT a rate-limit / interval constant (does not touch MIN/MAX_SEND_INTERVAL, LONG_PAUSE_*, FLOOD_HARD_THRESHOLD, the 24h pause, or per-sender rate_per_*), so the CLAUDE.md "не менять без обсуждения" carve-out does not apply.
</objective>
