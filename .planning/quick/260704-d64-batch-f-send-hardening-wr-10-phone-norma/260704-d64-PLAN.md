<objective>
Harden the n8n push endpoint `POST /api/v1/send` against three production defects surfaced in the
2026-07-03 checker/campaigns review (Батч F of the FIXPLAN):

- **WR-10** — `/send` passes `recipient_phone` through completely unnormalized. The identity key
  (`+E164` or `@handle`) is the join key across `campaign_contact_assignments`,
  `message_queue.recipient_phone`, `conversations.contact_phone`, `contacts_cache.phone`. A push of
  `89001234567` for a contact stored as `+79001234567` forks the identity: template vars go blank,
  rotation mints a second CCA identity, dedup can't see it, the same human gets two cold openers.
- **WR-11** — no campaign-status check (pushes into draft/done sit `pending` forever) and no
  idempotency (an n8n timeout→replay double-sends the same opener ~40s apart = spam signal).
- **IN-09** — the explicit `sender_slug` readiness check ignores `restriction_status`, so a
  `spam_limited`/`frozen` sender returns 200 and the item silently waits out the restriction.

Purpose: stop identity forking + duplicate cold openers + unsendable-forever rows on the live
n8n webhook path, and make the explicit-sender contract consistent with the rotation path.
Output: hardened `app/routers/send.py` (all four fixes) + `tests/test_send_hardening.py`, deployed
to prod and live-verified read-only.

Product-owner decisions (locked — do NOT re-ask):
- WR-11 dedup semantics = return-existing (200, idempotent), NOT reject/409 — chosen for
  n8n-retry-friendliness.
- WR-12-style CCA absorption policy is Batch E (already shipped) — out of scope here.

Prod fact (verified by orchestrator): `message_queue.recipient_phone` currently holds 249 valid
E.164 rows + 27 `@username` keys + 0 rows in any other format → enforcing normalization +
422-on-invalid is safe and will not break the live n8n flow (nothing currently sent fails the gate).
</objective>
