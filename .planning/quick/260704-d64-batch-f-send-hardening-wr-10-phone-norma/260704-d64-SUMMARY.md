# quick-260704-d64: Batch F — /send hardening (WR-10 / WR-11 / IN-09) Summary

Hardened the n8n push endpoint `POST /api/v1/send` against three production defects
(Batch F of the 2026-07-03 checker/campaigns FIXPLAN): unnormalized identity keys
(WR-10), no campaign-status guard + no idempotency (WR-11), and a restriction-blind
explicit-sender readiness check (IN-09). All four fixes live in one function, covered by
a new isolated regression file, deployed to prod and live-verified read-only.

## The four fixes (`app/routers/send.py`, function `send_message`)

1. **WR-10 — normalize-first identity key.** Introduced a local `recipient_key`:
   `@username` keys pass through unchanged; phone keys are forced to E.164 via
   `normalize_to_e164` (reused from `app.utils.phone`, not reimplemented); garbage →
   `422 INVALID_PHONE`. `recipient_key` is now threaded through rotation
   (`get_or_assign_sender`), contact lookup (`_lookup_contact_dict`), template render
   (`render_template(phone=...)`), enqueue (`enqueue_message(recipient_phone=...)`), and
   the final log line. `request.recipient_phone` is only READ (never mutated) inside the
   normalize block. This stops identity forking vs. the CSV-import / UI paths (the
   `+E164`/`@handle` join key across CCA / message_queue / conversations / contacts_cache).
2. **WR-11(a) — campaign-status guard.** A push into a non-running campaign
   (draft/paused/done) → `409 CAMPAIGN_NOT_RUNNING` with `detail.status`. Previously such
   items sat `pending` forever.
3. **WR-11(b) — idempotent replay dedup.** A duplicate `(campaign, recipient_key)` with an
   existing `pending`/`processing` queue row returns that EXISTING row (`200`, idempotent),
   with a fresh `_queue_position` / `_estimate_send_time`. No second `message_queue` insert;
   also short-circuits before rotation. Dedup keys off the normalized `recipient_key`, so a
   `+79001234567` first push and an `89001234567` replay resolve to the same row (an n8n
   timeout→replay no longer double-sends a cold opener ~40s apart).
4. **IN-09 — restriction-aware explicit-sender readiness.** The `if request.sender_slug:`
   branch now also rejects `restriction_status != 'none'` → `409 SENDER_NOT_READY` with
   `detail.restriction_status`, making the explicit-sender contract consistent with the
   rotation path (which already excludes restricted senders).
