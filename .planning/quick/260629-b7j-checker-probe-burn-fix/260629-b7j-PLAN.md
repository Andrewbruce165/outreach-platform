<objective>
Stop the contact-check health-probe from burning the checker pool. The probe (`_probe_cycle`)
currently fires every ~5s poll tick, ignores the Plan-14-07 `checker_rest_until` rest, isn't
counted against the per-checker daily budget, and a tripped checker auto-recovers in a fixed
~15min only to re-trip — measured at ~4,267 probe-batches/account/day on cycling checkers, exactly
the load that shadow-bans the contacts-API.

Purpose: make each checker's *total* contacts-API load (probe + resolve) stay under the empirical
~45-50 burst onset, and make a cycling checker back off for hours so the drain stops churning and
self-burning. The data layer is already correct (14-05 suspect-rollback); this is purely a
throughput/longevity fix layered on top WITHOUT changing the finalization rules.

Output: migration 036 (one new senders column), two new config knobs, four targeted edits to
`contact_check_worker.py`, and a RED-first test module.
</objective>
