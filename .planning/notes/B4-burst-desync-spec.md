# ТЗ: B4 — десинхронизация залпов отправки (burst desync)

**Статус:** proposal (не реализовано). Часть ремедиации C&C mass-ban.
**Дата:** 2026-08-18. **Автор контекста:** предыдущая сессия (см. memory `project-cc-campaign-mass-ban-analysis`).

---

## 1. Контекст и проблема

В mass-ban кампании «C&C - холодный аутрич» (`24658b65`) один из подтверждённых
кластерных признаков — **синхронный залп всего пула**. Из `message_queue`:

- **12-08 10:49** — по одному сообщению с шагом ~2 сек через ~20 свежих аккаунтов подряд.
- **17-08 15:38–15:43** — залп через все 32 аккаунта за несколько минут.

Для антиспама Telegram десятки аккаунтов, синхронно начинающие холодные диалоги
в одну минуту (часто с одинаковым текстом и общим `api_id`), — сильная подпись фермы.

### Почему так происходит (root cause)

Очередь настраивает тайминг **на уровне одного сендера**, а не сдвиг фаз **между**
сендерами:

- Базовый интервал 20–55 сек с fatigue-фактором — `app/services/queue.py:5, 44–52, ~786`.
- Пейс-джиттер внутри окна — `queue.py:~504` (`PACE_JITTER_LOW/HIGH`).
- Лимиты 4/мин, 20/час — per-sender (`queue.py:5–8`).
- Long-pause — `queue.py:378, 405, 424` (`long_pause_until`).

При **старте/resume кампании** у всех сендеров `senders.last_used_at` в далёком
прошлом → все одновременно проходят per-sender гейты и становятся «due» в одном
тике → синхронный залп. Никакой механизм не разносит **момент первой отправки**
между разными аккаунтами.

## 2. Цель / не-цель

**Цель:** сделать так, чтобы при старте/resume кампании отправки разных сендеров
были **разнесены во времени** и имели «человеческую» нерегулярность на уровне пула,
а не только внутри одного аккаунта.

**Не-цель / ЗАПРЕЩЕНО:**
- **НЕ трогать эмпирически подобранные интервалы** `rate_per_min` / `rate_per_hour` /
  базовый интервал 20–55с / fatigue / FloodWait. CLAUDE.md: «Очередь: не трогать
  интервалы без явного обсуждения». Комментарии в коде помечают их как PROTECTED
  (D-10, `queue.py:116–117, 651–652`). B4 добавляет **надстройку-гейт** «не раньше T»,
  но НЕ меняет сам base-interval.
- Не менять рабочие часы (`_campaign_in_working_window`, `queue.py:123`).

## 3. Важное замечание о приоритете

B4 — **дополнительный слой, не критичный фикс.** B1–H5 (задеплоены 2026-08-18,
commit `a5f92e1`) уже убрали два подтверждённых вектора смерти (беспрокси-кластер +
заморозка на send-time ImportContacts) и добавили видимую вариацию открывашки (H5,
LLM-перефраз, opt-in `campaigns.opener_paraphrase_enabled`). **Без видимой вариации
текста и без разнесения `api_id` (#8) B4 в одиночку косметичен** — синхронность лишь
один из сигналов. Делать B4 имеет смысл вместе с включённым H5.

## 4. Карта текущего кода (якоря, могут дрейфовать)

| Что | Файл |

| Send-воркер: батч-выборка eligible-сендеров | `app/services/queue.py::_tick` (~270–367) |
| Пик следующего item'а для сендера (LATERAL SELECT) | `queue.py::_process_next_for_sender` (~455–601) |
| Per-send гейт (интервал/лимиты/skip-until) | `queue.py::_check_rate_limits` (~641–790) |
| Готовые «skip until T» гейты (образец для B4) | `long_pause_until`, `proxy_switch_pending_at` (`queue.py:312–319`, `682–690`) |
| Рабочее окно кампании | `queue.py::_campaign_in_working_window` (123), `window_start` (167+) |
| Старт/resume кампании (status→running) | `app/routers/campaigns.py` (искать `status = 'running'`, start/resume/`requeue`) |

**Прецедент гейта:** `proxy_switch_pending_at` и `long_pause_until` — уже реализованные
per-sender «не выбирать этого сендера, пока NOW() < T» условия в выборке. B4 добавляет
такой же по смыслу гейт для стартового стаггера.

## 5. Предлагаемый механизм (минимально-рискованный)

### 5.1. Стартовый стаггер (ядро)

Новая per-sender метка **`send_stagger_until TIMESTAMPTZ NULL`** (миграция, идемпотентно;
ORM-колонка + server_default NULL — помнить про [[project-orm-default-vs-server-default-drift]]).

- При переходе кампании в `running` (первый старт И каждый resume) — для КАЖДОГО
  прикреплённого eligible-сендера выставить
  `send_stagger_until = NOW() + random_offset`, где `random_offset` равномерно
  распределён по окну `[0, STAGGER_WINDOW_SECONDS]`.
- Разброс детерминированно-случайный по сендеру: чтобы два сендера не получили один
  offset, использовать `random()` в SQL или `row_number()`-раскладку по окну
  (например `offset = i * (WINDOW / N) + jitter`).
- Send-воркер в выборке (`_check_rate_limits` и/или `_tick` батч-SELECT) добавляет
  условие-гейт: **пропустить сендера, пока `send_stagger_until > NOW()`** — по образцу
  `long_pause_until` (`queue.py:312`). Гейт снимается сам по истечении времени.
- Гейт трогает ТОЛЬКО первый выход сендера в окно; после первой отправки обычный
  base-interval 20–55с (нетронутый) продолжает работать.

### 5.2. Кап на одновременно активные сендеры (опционально, 2-й приоритет)

Ограничить число сендеров, отправивших за последнее короткое окно (например ≤K
сендеров с отправкой за последние 60с через весь пул кампании). Реализуемо как
дополнительное условие в `_tick` (COUNT distinct sender с `finished_at > NOW()-60s`).
Решить, нужно ли — при хорошем стаггере может быть избыточно.

### 5.3. Что НЕ трогаем

Base-interval 20–55с, fatigue, PACE_JITTER, long-pause, лимиты — без изменений.

## 6. Открытые решения (принять в сессии)

1. **Длина окна стаггера `STAGGER_WINDOW_SECONDS`** — зависит от размера пула и дневного
   объёма. Ориентир: разнести старт по 30–90 мин, но не дольше, чем окно рабочих часов.
   Сделать config-кнобом (`app/config.py`, Field + validation_alias).
2. **Применять стаггер на каждый resume или только на холодный старт?** (Рекоменд.:
   на каждый переход в running — resume после паузы это тоже «все стали due разом».)
3. **Раскладка offset:** чистый `random()` vs равномерная `i*(W/N)+jitter` (последняя
   гарантирует отсутствие случайных совпадений — предпочтительно).
4. **Кап одновременных сендеров (5.2)** — включать или нет.
5. **Только для холодных (new-dialog) отправок или для всех?** Фоллоу-апы к живым
   диалогам разносить не нужно — стаггер должен касаться только открытия новых диалогов.
   (В `_process_next_for_sender` уже есть разделение new-dialog vs follow-up — гейт
   вешать на new-dialog ветку.)
6. **Взаимодействие с H5:** имеет смысл в UI/логике связать включение стаггера с
   `opener_paraphrase_enabled` или сделать отдельный флаг кампании
   `desync_enabled` (default off, opt-in).

## 7. Реализация (эскиз)

1. **Миграция** `NNN_sender_send_stagger.sql`: `ALTER TABLE senders ADD COLUMN IF NOT
   EXISTS send_stagger_until TIMESTAMPTZ;` + ORM-колонка в `Sender`.
2. **Config**: `send_stagger_window_seconds` (+ опц. `max_concurrent_senders_window`).
3. **Установка стаггера** при старте/resume: в `campaigns.py` (endpoint перехода в
   running) и/или в `rebalance.py`. Один set-based UPDATE, раскладывающий offset по
   прикреплённым eligible-сендерам.
4. **Гейт в выборке**: добавить `AND (s.send_stagger_until IS NULL OR
   s.send_stagger_until <= NOW())` в new-dialog ветку `_process_next_for_sender` и/или
   skip в `_check_rate_limits` (зеркало `long_pause_until`).
5. **Опц. кап** (5.2) — отдельным условием.
6. Опц. флаг кампании `desync_enabled` (миграция + модель + схема + роутер, по образцу
   `variation_enabled` / `opener_paraphrase_enabled`).

## 8. Тестирование (обязательно через test-overlay)

`docker compose -f docker-compose.yml -f docker-compose.test.yml run --rm api pytest`

Кейсы:
- Старт кампании раскладывает `send_stagger_until` по N сендерам внутри окна (все
  различны, ∈ `[NOW(), NOW()+W]`).
- Сендер с `send_stagger_until > NOW()` НЕ выбирается для НОВОГО диалога, но фоллоу-ап
  к существующему диалогу проходит (стаггер только на new-dialog).
- По истечении стаггера сендер выбирается; base-interval 20–55с НЕ изменён (регресс на
  существующих тестах `_check_rate_limits`, напр. `tests/test_send.py`).
- (если 5.2) при ≤K активных за окно лишние сендеры пропускаются.
- Регресс: очередь/rebalance/enqueue тесты зелёные (`test_queue_new_dialog_limit`,
  `test_send`, `test_send_hardening`, `test_rebalance`, `test_campaign_enqueue_worker`).

## 9. Верификация вживую (после деплоя)

На тестовой холодной кампании после старта проверить `message_queue`:
- нет ≥5 отправок в одну минуту через весь пул (`finished_at` разнесены);
- первые отправки сендеров размазаны по окну стаггера, а не в один тик.

## 10. Риск / откат

- Риск низкий: гейт аддитивный, base-interval не тронут. Флаг `desync_enabled`
  (или config-кноб `send_stagger_window_seconds=0` → эффективно выкл) даёт мгновенный
  откат без релиза.
- Осторожно с ORM-колонкой: server_default + явное значение (см. память про
  create_all-drift), иначе fresh-DB/recovery упадёт.
- Помнить fail-fast миграций (api не стартует при падении миграции) — миграция обязана
  быть идемпотентной.

## 11. Definition of Done

- [ ] Стаггер раскладывается при старте/resume; сендеры не стартуют синхронно.
- [ ] Base-interval 20–55с / лимиты не изменены (регресс зелёный).
- [ ] Стаггер только на new-dialog, фоллоу-апы не задержаны.
- [ ] Config-кноб + (опц.) флаг кампании; выключаемо без релиза.
- [ ] Тесты через test-overlay зелёные; живая проверка `message_queue` показывает
      разнесённые старты.
